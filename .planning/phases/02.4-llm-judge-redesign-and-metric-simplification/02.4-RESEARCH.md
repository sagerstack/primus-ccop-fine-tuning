# Phase 2.4: LLM Judge Redesign and Metric Simplification - Research

**Researched:** 2026-03-22
**Domain:** LLM-as-judge evaluation, RAG hallucination detection, compliance domain reasoning
**Confidence:** HIGH

## Summary

This research investigates the implementation approach for redesigning the LLM Judge from 15 per-benchmark rubric dimensions to 2 universal dimensions (reasoning depth + hallucination check). The key challenge: RAGAs metrics handle factual quality (coverage, relevance, grounding), while the LLM Judge should handle what only an LLM can assess—reasoning quality and hallucination detection.

**Current system state:**
- LLM Judge: Claude Sonnet evaluating B3, B7-B20 using benchmark-specific rubrics (0-3 anchored scale)
- Rule-based: B1, B2, B4-B6, B21 using keyword/Jaccard/regex scoring
- RAGAs: 7 metrics (factual_precision, factual_recall, answer_relevancy, semantic_similarity, context_faithfulness, context_precision, context_recall)
- Scoring formula: ragas_score = (factual_recall + factual_precision + answer_relevancy)/3 * factual_precision

**Primary recommendation:** Use 0-3 anchored scale for both dimensions with universal adaptive rubrics, pass retrieved contexts to judge for claim verification, keep binary hallucination flag (pass/fail) separate from graded reasoning depth, and migrate B21 to LLM Judge while keeping B1-B6 rule-based. Chain-of-Thought prompt engineering with separate dimension evaluation.

## Research Findings by Topic

### 1. LLM-as-Judge Reasoning Depth Evaluation

#### Scoring Scale: 0-3 vs 0-5 vs Binary

**Recommendation: 0-3 anchored scale** (maintain current system)

**Evidence:**
- Binary or low-precision scoring (0-3) produces more reliable results than high-precision scales (0-5, 0-10) because LLMs struggle to calibrate fine-grained distinctions consistently ([EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-as-a-judge), [AWS Blog](https://aws.amazon.com/blogs/machine-learning/evaluate-generative-ai-models-with-an-amazon-nova-rubric-based-llm-judge-on-amazon-sagemaker-ai-part-2/))
- High-precision scales cause evaluators (both human and LLM) to struggle maintaining consistent standards for the same score, resulting in less consistent output ([GoDaddy Blog](https://www.godaddy.com/resources/news/calibrating-scores-of-llm-as-a-judge))
- 0-3 scales retain precision compared to 0-10 or 0-100 while making it considerably easier to provide grading rubrics ([Confident AI](https://www.confident-ai.com/blog/why-llm-as-a-judge-is-the-best-llm-evaluation-method))
- Current system already uses 0-3 with clear anchoring—no migration cost

**Trade-offs:**
- 0-3 anchored: Lower granularity but higher consistency and interpretability
- 0-5: More granularity but struggles with "what's the difference between 3 and 4?" consistency problems
- Binary: Highest consistency but loses nuance needed for reasoning depth assessment

**Confidence:** HIGH (multiple 2025-2026 sources, aligns with current implementation)

#### Universal vs Adaptive Rubric

**Recommendation: Universal adaptive rubric** (generates question-specific criteria from universal principles)

**Evidence:**
- Adaptive rubrics generate tailored pass/fail checks that reflect what "good" means for each specific input/output/context combination—particularly valuable for agentic workloads because interactions are rarely uniform ([Medium](https://medium.com/@aiforhuman/rubric-based-evaluation-for-agentic-systems-db6cb14d8526))
- Question-specific rubrics tailored to problem statements perform better for logical assessment than question-agnostic rubrics emphasizing generic criteria ([ACM Conference](https://dl.acm.org/doi/10.1145/3702652.3744220))
- Adaptive rubrics can choose evaluation questions to maximize expected information gain and stop at diminishing returns ([ArXiv LLM-Rubric](https://arxiv.org/html/2501.00274v1))
- Static rubrics apply consistent criteria but miss context-specific nuances

**Implementation approach:**
- Define universal principles (clause citations + conditional analysis + actionable steps) in the judge prompt
- Let the judge adapt these principles to the specific question context
- Example: For "MFA requirements for admin accounts," judge adapts to check for clause 5.3.1 citations, CIIO admin role conditions, and concrete MFA implementation steps

**Trade-offs:**
- Universal adaptive: Higher quality evaluations, context-aware, but requires sophisticated prompt engineering
- Static universal: Simpler implementation, consistent across questions, but may miss domain-specific nuances

**Confidence:** HIGH (recent 2025-2026 research, aligns with compliance domain complexity)

#### Reference-Free vs Reference-Guided

**Recommendation: Reference-free for reasoning depth** (judge should NOT see expected_response when scoring reasoning)

**Evidence:**
- Reference-free evaluation enables assessment when ground truth is unavailable or multiple correct answers exist—critical for open-ended reasoning tasks ([Braintrust](https://www.braintrust.dev/articles/llm-evaluation-metrics-guide), [EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-evaluation-metrics))
- Reasoning quality is inherently reference-free: deep reasoning can manifest in multiple valid forms (different clauses cited, different conditional paths) as long as structure is present
- Reference-guided evaluation risks penalizing valid alternative reasoning paths that differ from the expected answer
- Use reference-based evaluation only for objective factual correctness ([ArXiv Reference-Guided](https://arxiv.org/html/2408.09235))

**Motivating example from context:**
- B3-001 response introduced valid reasoning (individual accountability, shared account principles) that was penalized by factual_precision
- The reasoning was structurally sound (clause citations + conditionals + actionable steps) even though specific clauses differed from expected answer

**Trade-offs:**
- Reference-free: Allows valid alternative reasoning, but requires judge to assess structure/quality independently
- Reference-guided: Easier to score (compare to gold standard), but penalizes valid alternatives

**Confidence:** HIGH (aligns with motivating problem, supported by evaluation literature)

### 2. LLM-based Hallucination Detection in RAG Systems

#### Optimal Context Passing to Judge

**Recommendation: Pass full retrieved chunks** (not citations or summaries)

**Evidence:**
- Span-level verification (checking each claim against retrieved evidence) is the most robust 2025-2026 approach ([Lakera](https://www.lakera.ai/blog/guide-to-hallucinations-in-large-language-models), [Deepchecks](https://deepchecks.com/llm-hallucination-detection-and-mitigation-best-techniques/))
- Faithfulness evaluation requires breaking down answers into atomic claims and checking each against retrieved context—requires full context, not summaries ([RAG Evaluation 2026](https://blog.premai.io/rag-evaluation-metrics-frameworks-testing-2026/))
- Cheap embedding checks are ineffective for RLHF models; reliable safety requires expensive reasoning (LLM-as-Judge) with full context ([ArXiv FACTUM](https://arxiv.org/pdf/2601.05866))
- Passing citations only or summaries prevents judge from verifying specific claim-to-evidence grounding

**Implementation approach:**
- Pass `retrieved_contexts` (list of full chunk texts) directly to judge
- Judge performs claim extraction → verification against full chunks
- Similar to current RAGAs faithfulness metric implementation

**Trade-offs:**
- Full chunks: Accurate verification but higher token cost for judge
- Citations only: Lower cost but judge cannot verify claims
- Summary: Medium cost but lossy—judge may miss contradictions

**Confidence:** HIGH (state of the art 2026, aligns with RAGAs design)

#### Binary vs Graded Hallucination Scoring

**Recommendation: Binary pass/fail** (separate from reasoning depth score)

**Evidence:**
- Binary evaluations (e.g., "Polite" vs "Impolite") are more reliable and consistent for both LLMs and human evaluators—easier to get accurate results with two simple choices ([EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-as-a-judge))
- Hallucination detection as binary classification achieves good accuracy in RAG systems in zero-shot setting, with training on synthetic data further improving detection ([Quantifying Hallucination](https://aclanthology.org/2025.findings-naacl.433.pdf))
- In compliance domains, hallucination severity matters less than presence: a response citing fabricated clauses fails regardless of severity
- Graded scoring (1-5 faithfulness) introduces calibration challenges and doesn't change the failure outcome

**Implementation approach:**
- Binary flag: `hallucination_detected` (boolean)
- Keep reasoning_depth as separate 0-3 graded score
- A response can have deep reasoning (3/3) but fail hallucination check (hallucination_detected=True)
- Scoring formula uses boolean as gate: `if hallucination_detected: benchmark_score = 0; else: benchmark_score = reasoning_depth/3.0`

**Trade-offs:**
- Binary: Clear pass/fail, consistent, simple to interpret
- Graded (1-5): More nuance on severity, but introduces calibration complexity and doesn't change failure outcome in compliance

**Confidence:** HIGH (aligns with compliance domain requirements, supported by evaluation literature)

#### Hallucination Severity Taxonomy

**Recommendation: Distinguish "unsupported claim" from "contradicted claim"** (2-level taxonomy)

**Evidence:**
- Hallucination types: Contradictions (claims directly against context) vs Unsupported Claims (not grounded in context) ([RAG Evaluation 2026](https://blog.premai.io/rag-evaluation-metrics-frameworks-testing-2026/))
- In compliance domains, both types are failures but contradictions are more severe (incorrect legal interpretation vs missing citation)
- Comprehensive taxonomies differentiate intrinsic (contradicting input) vs extrinsic (inconsistent with training data), and factuality (absolute correctness) vs faithfulness (adherence to input) ([ArXiv Hallucination Taxonomy](https://arxiv.org/pdf/2508.01781))
- FINRA 2026 regulatory report: firms must develop procedures to catch hallucinations in AI systems ([WealthManagement](https://www.wealthmanagement.com/regulation-compliance/finra-cautions-broker-dealers-to-catch-hallucinations-when-using-gen-ai))

**Implementation approach:**
- Judge classifies each claim as: `SUPPORTED`, `UNSUPPORTED`, or `CONTRADICTED`
- Binary flag: `hallucination_detected = (any claim is UNSUPPORTED or CONTRADICTED)`
- Store severity metadata for analysis: `{"unsupported_count": N, "contradicted_count": M}`
- Both types trigger failure, but metadata enables deeper analysis

**Trade-offs:**
- 2-level taxonomy: Balances simplicity with diagnostic value
- Single binary: Simplest but loses diagnostic information
- Full taxonomy (8+ types): Maximum detail but complexity outweighs value in compliance domain

**Confidence:** MEDIUM (compliance domain requirements clear, but 2-level taxonomy is practical middle ground not explicitly recommended in literature)

#### LLM-Only Mode: Shadow Retrieval

**Recommendation: Implement shadow retrieval for LLM-only mode** (retrieve for judge, not for model)

**Evidence:**
- RAG can still produce hallucinations: model may misread, over-generalize, or fabricate claims even when given relevant context ([Towards Data Science](https://towardsdatascience.com/detecting-hallucination-in-rag-ecaf251a6633/))
- Internal detection methods like Cross-Layer Attention Probing (CLAP) train classifiers on model activations for real-time hallucination flagging when external verification isn't possible ([Must-Attend AI](https://deepchecks.com/llm-hallucination-detection-and-mitigation-best-techniques/))
- Shadow retrieval concept: retrieve chunks but only pass to judge, not to model—decouples retrieval-for-grounding from retrieval-for-evaluation
- Enables hallucination detection in LLM-only mode without changing model behavior

**Implementation approach:**
- LLM-only mode: Model generates from own knowledge (no retrieved_contexts passed to model)
- Evaluation layer: Retrieve contexts in background → pass to judge for hallucination check
- Judge evaluates: "Does this response make claims that contradict or aren't supported by what RAG would have provided?"
- Enables consistent hallucination metric across both modes (hybrid and LLM-only)

**Trade-offs:**
- Shadow retrieval: Consistent evaluation across modes, but adds retrieval cost to LLM-only mode
- No retrieval in LLM-only: Lower cost, but can't detect hallucination (must skip metric)

**Confidence:** MEDIUM (concept well-supported but "shadow retrieval" terminology not standard—combine internal detection techniques with standard RAG evaluation patterns)

#### Claim-Level vs Response-Level Detection

**Recommendation: Claim-level detection with response-level flag** (fine-grained diagnostic + binary gate)

**Evidence:**
- Span-level verification (each claim matched against evidence) is most promising for actionable feedback and selective grounding ([Lakera](https://www.lakera.ai/blog/guide-to-hallucinations-in-large-language-models))
- Faithfulness evaluation involves claim extraction → verification → scoring per claim ([RAG Evaluation 2026](https://blog.premai.io/rag-evaluation-metrics-frameworks-testing-2026/))
- Sentence-level scores crucial for actionable feedback and identifying which specific claims are problematic ([Must-Attend AI](https://deepchecks.com/llm-hallucination-detection-and-mitigation-best-techniques/))
- Response-level percentage (responses containing at least one hallucination) is primary metric for overall hallucination rates ([Medium Hallucination Rates](https://medium.com/@markus_brinsa/hallucination-rates-in-2025-accuracy-refusal-and-liability-aa0032019ca1))

**Implementation approach:**
- Judge performs claim extraction (break response into atomic claims)
- Verify each claim → classify as SUPPORTED/UNSUPPORTED/CONTRADICTED
- Store claim-level metadata: `{"claims": [{"text": "...", "status": "SUPPORTED"}, ...]}`
- Response-level flag: `hallucination_detected = (any claim is UNSUPPORTED or CONTRADICTED)`
- Use response-level flag for scoring gate, claim-level data for diagnostics

**Trade-offs:**
- Claim-level: Fine-grained diagnostics, actionable feedback, but higher evaluation complexity
- Response-level: Simpler binary flag, but loses diagnostic granularity

**Confidence:** HIGH (clear consensus in 2026 literature, aligns with best practices)

### 3. RAGAs Scoring Formula Design

#### Current Formula Assessment

**Current formula:** `ragas_score = (factual_recall + factual_precision + answer_relevancy)/3 * factual_precision`

**Assessment:** Multiplicative penalty is problematic with new LLM Judge design

**Evidence:**
- Motivating problem: B3-001 introduced valid reasoning but scored 0.27 on factual_precision (precision mode of FactualCorrectness metric)
- Formula applies factual_precision as multiplicative penalty: `base * factual_precision`
- This penalizes valid inference that differs from expected_response—exactly what the phase aims to fix
- RAGAs framework uses additive combination by default: faithfulness, context relevance, answer relevance are independent dimensions ([ArXiv RAGAs](https://arxiv.org/html/2309.15217v2))

**Key insight from codebase:**
- `factual_precision` = `FactualCorrectness(mode="precision")` in RAGAs
- This compares response claims to reference using NLI (natural language inference)
- Valid compliance reasoning can cite different (but correct) clauses → low precision vs reference
- This is not hallucination—it's alternative valid reasoning

**Confidence:** HIGH (direct evidence from motivating problem, codebase analysis)

#### Recommended Formula Change

**Recommendation: Remove factual_precision multiplicative penalty** (make dimensions independent)

**New formula:** `ragas_score = (factual_recall + answer_relevancy + semantic_similarity)/3`

**Rationale:**
- LLM Judge reasoning_depth dimension now handles reasoning quality assessment
- LLM Judge hallucination_detected dimension handles grounding/fabrication detection
- RAGAs dimensions should measure orthogonal quality aspects:
  - `factual_recall`: Coverage of reference key points (what's included)
  - `answer_relevancy`: Relevance to question (on-topic)
  - `semantic_similarity`: Semantic alignment with reference (how similar)
  - `context_faithfulness`: Grounding in retrieved chunks (RAG only)
  - `context_precision`: Retrieval quality - relevant chunks first (RAG only)
  - `context_recall`: Retrieval completeness - all relevant chunks retrieved (RAG only)
- Remove `factual_precision` entirely: this metric penalizes valid alternative reasoning and duplicates LLM Judge hallucination check

**Alternative considered:**
- Keep multiplicative penalty but use `context_faithfulness` instead: `ragas_score = base * context_faithfulness`
- **Rejected:** context_faithfulness upper bounds hallucination (0.80 in B3-001) but can't distinguish valid inference from fabrication—insufficient precision for compliance domain

**Trade-offs:**
- Independent dimensions: Clearer interpretation, doesn't penalize valid alternatives, aligns with RAGAs design
- Multiplicative penalty: Stronger signal for unfaithful responses, but penalizes valid reasoning

**Confidence:** HIGH (addresses motivating problem, aligns with RAGAs framework design)

#### Combined vs Independent Scores

**Recommendation: Independent scores** (Benchmark Score + RAGAs Score reported separately)

**Evidence:**
- Multi-dimensional evaluation provides richer analysis: a response can score high on RAGAs but low on benchmarks, or vice versa ([RAG Evaluation 2026](https://blog.premai.io/rag-evaluation-metrics-frameworks-testing-2026/))
- RAGAs and LLM Judge measure orthogonal quality aspects:
  - RAGAs: Generic response quality (factual coverage, relevance, semantic similarity, retrieval quality)
  - LLM Judge: Domain-specific compliance quality (reasoning depth, hallucination detection)
- Combining into single score obscures which dimension caused failure
- Independent scores enable diagnostic analysis: "response is semantically similar but lacks reasoning depth"

**Implementation approach:**
- Report both scores separately in evaluation results
- CLI flag `--threshold` applies to Benchmark Score only (LLM Judge overall_score)
- RAGAs scores are diagnostic, not pass/fail gates
- Users can analyze correlation: "Do low RAGAs scores predict low benchmark scores?"

**Trade-offs:**
- Independent: Richer diagnostics, clear dimension separation, but two scores to track
- Combined: Single quality metric, simpler reporting, but loses diagnostic value

**Confidence:** HIGH (current system already separates them, aligns with evaluation best practices)

### 4. Rule-based vs LLM Judge Migration

#### Should Rule-based Benchmarks Migrate?

**Recommendation: Migrate B21 to LLM Judge, keep B1-B6 rule-based**

**Evidence:**
- Multi-layered evaluation pipelines combine deterministic checks (fast, cheap, reproducible) with LLM judges (semantic, nuanced) ([Dev.to](https://dev.to/anshd_12/deterministic-vs-llm-evaluators-a-2026-technical-trade-off-study-11h))
- Senior Evaluation Engineers build pipelines running fast deterministic checks first, then escalating to LLM judges for nuanced assessment ([EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-as-a-judge))
- Programmatic rule evaluations run instantly, cost nothing per execution, produce perfectly reproducible results ([Label Your Data](https://labelyourdata.com/articles/llm-as-a-judge))
- LLM judges handle nuance but add cost, latency, and non-determinism ([Braintrust](https://www.braintrust.dev/articles/what-is-llm-as-a-judge))

**Benchmark-by-benchmark analysis:**

| Benchmark | Type | Current Metric | Recommendation | Rationale |
|-----------|------|----------------|----------------|-----------|
| B1 | Rule-based | Keyword accuracy | **Keep rule-based** | Label matching is deterministic, no reasoning depth needed |
| B2 | Rule-based | Citation accuracy | **Keep rule-based** | Regex citation extraction is objective, reproducible |
| B4 | Rule-based | Terminology accuracy | **Keep rule-based** | Keyword matching for technical terms is sufficient |
| B5 | Rule-based | Classification accuracy | **Keep rule-based** | Label classification is objective |
| B6 | Rule-based | Violation detection | **Keep rule-based** | Keyword-based violation detection is deterministic |
| B21 | Rule-based | Hallucination (regex) | **MIGRATE to LLM Judge** | Binary regex is insufficient—need claim-level semantic verification |

**B21 migration rationale:**
- Current B21 uses regex pattern matching for fabricated clause detection—too simplistic
- New LLM Judge hallucination dimension provides claim-level verification with context grounding
- Hallucination detection requires semantic understanding, not pattern matching
- Aligns with research: cheap embedding checks ineffective, reliable detection requires reasoning ([ArXiv FACTUM](https://arxiv.org/pdf/2601.05866))

**Trade-offs:**
- Keep rule-based (B1-B6): Fast, cheap, reproducible, but no reasoning depth assessment
- Migrate to LLM (B21): Semantic understanding, claim-level precision, but adds cost/latency

**Confidence:** HIGH (clear cost/benefit trade-off, aligns with multi-layered pipeline best practices)

### 5. Judge Prompt Engineering

#### Multi-Dimensional Evaluation: Single vs Separate Prompts

**Recommendation: Single prompt with structured output** (evaluate both dimensions in one call)

**Evidence:**
- When checking different dimensions (like tone and accuracy), split them into separate evaluations to maintain focus ([EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-as-a-judge))
- **However**, this recommendation applies to UNRELATED dimensions (tone ≠ accuracy)
- Reasoning depth and hallucination check are RELATED: both analyze the same claims
- Single-prompt strategy for related dimensions: LLM-EVAL evaluates performance across multiple related dimensions (content, grammar, relevance, appropriateness) in one call ([ArXiv LLMs-as-Judges](https://arxiv.org/html/2412.05579v2))
- Legal domain example: three-stage hierarchical prompt structure with multi-dimensional response assessment in single call ([Nature Scientific Reports](https://www.nature.com/articles/s41598-025-30306-9))

**Implementation approach:**
```
PROMPT STRUCTURE:
1. Task: Evaluate compliance response quality
2. Inputs: question, response, retrieved_contexts
3. Process:
   Step 1: Extract atomic claims from response
   Step 2: For each claim, verify against contexts (SUPPORTED/UNSUPPORTED/CONTRADICTED)
   Step 3: Assess reasoning depth (clause citations + conditionals + actionable steps)
4. Output: JSON with {
   "claims": [{"text": "...", "status": "..."}],
   "hallucination_detected": bool,
   "reasoning_depth_score": 0-3,
   "justification": "..."
}
```

**Trade-offs:**
- Single prompt: More efficient (one API call), shared claim analysis, but longer prompt
- Separate prompts: Simpler per-prompt, but redundant claim extraction, 2x API calls

**Confidence:** HIGH (dimensions are related, single prompt is standard for multi-dimensional analysis)

#### Chain-of-Thought vs Direct Scoring

**Recommendation: Chain-of-Thought with structured reasoning** (CoT before scoring)

**Evidence:**
- Chain-of-thought prompting improves reliability by 10-15% and provides debuggable reasoning trails ([EvidentlyAI](https://www.evidentlyai.com/llm-guide/llm-as-a-judge), [Confident AI](https://www.confident-ai.com/blog/why-llm-as-a-judge-is-the-best-llm-evaluation-method))
- CoT improves correlation with human judgments: G-Eval research showed improvement from 0.51 to 0.66 Spearman ρ on summarization ([Label Your Data](https://labelyourdata.com/articles/llm-as-a-judge))
- Never ask judge to just output a number—always prompt for step-by-step reasoning before final score ([Using LLMs for Evaluation](https://cameronrwolfe.substack.com/p/llm-as-a-judge))
- Current LLM Judge service already uses CoT instruction in rubric prompts

**Implementation approach:**
```
Step-by-step reasoning:
1. CLAIM EXTRACTION: List each atomic claim in the response
2. CLAIM VERIFICATION: For each claim, check against retrieved contexts
   - SUPPORTED: Direct evidence in context
   - UNSUPPORTED: No evidence (missing citation)
   - CONTRADICTED: Evidence contradicts claim
3. REASONING DEPTH: Check for three layers
   - Clause citations: Specific CCoP clauses referenced (0-1)
   - Conditional analysis: "If X then Y" logic (0-1)
   - Actionable steps: Concrete CIIO actions (0-1)
4. SCORING: Sum reasoning depth layers → 0-3 score
5. JUSTIFICATION: Explain score with evidence from response
```

**Trade-offs:**
- CoT: Higher reliability, debuggable, explainable, but slightly higher token cost
- Direct scoring: Lower token cost, faster, but less reliable and no debugging trail

**Confidence:** HIGH (established best practice, current system already uses CoT)

#### Including Retrieved Context Without Bias

**Recommendation: Pass contexts as verification grounding, not as answer guide**

**Evidence:**
- Factual verification without reference context is the most common LLM judge failure—judge defaults to "sounds plausible" assessment, and confident hallucinations score high ([Katherine Munro](https://katherine-munro.com/p/practical-problems-with-llms-as-judges))
- Reference-guided scoring gives judge the reference solution to help with scoring ([Braintrust](https://www.braintrust.dev/articles/llm-evaluation-metrics-guide))
- But retrieved contexts ≠ reference solution: contexts are evidence, reference is expected answer

**Implementation approach:**
- Prompt structure:
  ```
  QUESTION: {question}
  RESPONSE: {response}
  RETRIEVED CONTEXTS: {contexts}

  Your task: Verify each claim in RESPONSE against RETRIEVED CONTEXTS.
  Do NOT use RETRIEVED CONTEXTS to determine what the answer should be.
  Only use them to check: "Is this claim supported by evidence?"

  A claim can be SUPPORTED even if it cites different clauses than expected,
  as long as the cited clauses are factually correct per RETRIEVED CONTEXTS.
  ```
- Explicitly instruct judge to use contexts for verification, not prescription
- Aligns with reference-free reasoning depth (don't bias toward specific answer structure)

**Trade-offs:**
- Contexts for verification: Enables accurate hallucination check without biasing reasoning assessment
- No contexts: Can't verify grounding (must skip hallucination metric)

**Confidence:** HIGH (addresses common pitfall, aligns with reference-free recommendation)

## Common Pitfalls to Avoid

### 1. Factual Verification Without Context (CRITICAL)

**Pitfall:** Judge evaluates response plausibility instead of grounding, scoring confident hallucinations high.

**Prevention:**
- Always pass retrieved_contexts to judge for hallucination dimension
- Implement shadow retrieval for LLM-only mode (retrieve for judge, not model)
- Explicit prompt instruction: "Verify claims against contexts, not plausibility"

**Warning signs:** High hallucination scores on responses with fabricated clauses

### 2. Position and Verbosity Bias

**Pitfall:** GPT-4 shows ~40% position bias (flips decision when swapping answer order), ~15% verbosity bias (longer answers score higher).

**Prevention:**
- Our system doesn't do pairwise comparison (no position bias risk)
- Use 0-3 scale with clear anchoring (mitigates verbosity bias)
- Explicit rubric criteria for reasoning depth, not length

**Warning signs:** Longer responses consistently score higher regardless of quality

### 3. Mixing Valid Inference with Hallucination

**Pitfall:** Penalizing valid alternative reasoning as hallucination because it differs from expected answer.

**Prevention:**
- Reference-free reasoning depth evaluation (don't compare to expected_response)
- Hallucination check only verifies grounding in contexts, not match to reference
- 2-level taxonomy: SUPPORTED vs UNSUPPORTED/CONTRADICTED (valid inference = SUPPORTED)

**Warning signs:** Low scores on structurally sound responses citing different (but correct) clauses

### 4. Scope Creep: LLM Judge Doing RAGAs Work

**Pitfall:** Judge evaluating relevance, semantic similarity, recall—duplicating RAGAs metrics.

**Prevention:**
- Clear dimension separation:
  - LLM Judge: Reasoning depth, hallucination detection (compliance-specific)
  - RAGAs: Factual coverage, relevance, similarity (generic quality)
- Don't ask judge "Is this answer relevant?" (that's answer_relevancy metric)

**Warning signs:** Judge justifications mentioning "answer is relevant" or "semantically similar"

### 5. Non-Determinism Without Awareness

**Pitfall:** Judge is non-deterministic—scale changes every evaluation run, making regression testing unreliable.

**Prevention:**
- Accept non-determinism for reasoning assessment (LLMs excel here, deterministic tools don't)
- Use rule-based metrics (B1-B6) for regression-sensitive dimensions
- Build validation set with human ground truth (~50 examples) to monitor judge drift

**Warning signs:** Same response scores differently across runs with >0.3 variation

### 6. Specialized Domain Over-Confidence

**Pitfall:** Judge overlooks subtle compliance mistakes (incorrect clause interpretation, misapplied legal standards) that general-purpose models don't consistently catch.

**Prevention:**
- Validate judge with domain expert review on sample of evaluations
- Use adaptive rubric with compliance-specific criteria (clause citations, conditional logic)
- Maintain human-in-the-loop for high-stakes evaluations

**Warning signs:** Expert review finds errors judge marked as correct

```python
QUESTION: {question}
RESPONSE: {response}
RETRIEVED CONTEXTS: {contexts}

TASK: Detect hallucinations (claims not grounded in contexts).

STEP 1 - CLAIM EXTRACTION:
Break the response into atomic claims. Each claim should be a single factual statement.

Example:
Response: "Clause 5.3.1 requires MFA for admin accounts. CIIOs should implement hardware tokens."
Claims:
1. "Clause 5.3.1 requires MFA for admin accounts"
2. "CIIOs should implement hardware tokens"

STEP 2 - CLAIM VERIFICATION:
For each claim, verify against RETRIEVED CONTEXTS:
- SUPPORTED: Direct evidence in contexts (quote the supporting text)
- UNSUPPORTED: No evidence in contexts (missing citation, claim not grounded)
- CONTRADICTED: Evidence contradicts claim (cite contradicting text)

CRITICAL: A claim citing a different clause than expected is SUPPORTED if that clause
is factually correct per the contexts. Valid inference ≠ hallucination.

STEP 3 - VERDICT:
hallucination_detected = True if ANY claim is UNSUPPORTED or CONTRADICTED

Output as JSON:
{{
  "claims": [
    {{"text": "...", "status": "SUPPORTED|UNSUPPORTED|CONTRADICTED", "evidence": "..."}},
    ...
  ],
  "hallucination_detected": true/false,
  "unsupported_count": N,
  "contradicted_count": M
}}
"""
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| Per-benchmark custom rubrics | Universal adaptive rubrics | 2025-2026 | Higher consistency, context-aware evaluation |
| Response-level hallucination | Claim-level verification | 2025-2026 | Fine-grained diagnostics, actionable feedback |
| Embedding-based similarity checks | LLM-as-judge reasoning | 2026 | Reliable for RLHF models, semantic understanding |
| Binary hallucination (regex) | Graded severity taxonomy | 2025-2026 | Distinguishes unsupported vs contradicted |
| Separate factual + reasoning scores | Integrated multi-dimensional evaluation | 2026 | Single prompt, shared claim analysis |

**Deprecated/outdated:**
- High-precision scales (0-10, 0-100): LLMs can't calibrate consistently, use 0-3 or 0-5 max
- Multiplicative penalty formulas (base * factual_precision): Penalizes valid alternative reasoning
- Rule-based hallucination detection (regex): Insufficient for semantic verification, migrate to LLM judge
- Generic LLM judges without domain rubrics: Specialized domains (legal, medical, compliance) require explicit criteria

## Critical Addition: Model System Prompt Alignment

**Finding (post-research, from user review):** The evaluation criteria and the model's system prompt must be aligned. If the judge scores on clause citations + conditional analysis + actionable CIIO steps, but the system prompt never tells the model to produce those, the model is scored on expectations it doesn't know about.

**Current gap:** The RAG generation system prompt gives general CCoP instructions without specifying response structure expectations (cite specific clauses, analyze conditions, provide actionable steps).

**Recommendation:** Redesign the generation node system prompt to explicitly guide the model toward:
1. Citing specific CCoP clauses from retrieved context (e.g., "Clause 5.3.1(c)")
2. Analyzing conditions and trade-offs in the compliance scenario
3. Providing concrete actionable steps for the CIIO

**Scope:** This is included in Phase 2.4 — the system prompt and judge criteria are two sides of the same coin. Designing them together ensures consistency.

**Implementation note:** The system prompt lives in the generation node of the RAG pipeline. Changes affect both hybrid and llm-only modes.

## Open Questions

### 1. Shadow Retrieval Implementation Strategy

**What we know:**
- Concept is sound: retrieve for judge evaluation, not for model generation
- Enables consistent hallucination metric across hybrid and LLM-only modes
- Adds retrieval cost to LLM-only mode

**What's unclear:**
- Should shadow retrieval use same retriever as hybrid mode, or simplified retriever?
- How to handle retrieval failures in shadow mode (skip metric vs use empty contexts)?

**Recommendation:**
- Use same retriever as hybrid mode for consistency
- If retrieval fails: skip hallucination metric, flag as `hallucination_check_skipped=True`
- Log shadow retrieval as distinct operation for cost tracking

### 2. Judge Model Selection: Claude Sonnet vs GPT-4o vs Gemini Pro

**What we know:**
- Current system uses Claude Sonnet
- GPT-4 achieves 80% agreement with human evaluators ([Label Your Data](https://labelyourdata.com/articles/llm-as-a-judge))
- Models with strong instruction-following and reasoning (GPT-4o, Claude Sonnet, Gemini Pro) are standard

**What's unclear:**
- Has Claude Sonnet been validated against human ground truth for this compliance domain?
- Would multi-judge ensemble (Claude + GPT-4o) improve reliability vs cost trade-off?

**Recommendation:**
- Keep Claude Sonnet as primary judge (current implementation, strong reasoning)
- Build validation set with 50-100 human-labeled examples
- Measure judge-human agreement → if <80%, consider GPT-4o or ensemble

### 3. Threshold Calibration for 2-Dimension Scoring

**What we know:**
- Current system: `--threshold` applies to benchmark_score (0.0-1.0)
- New system: binary hallucination flag + reasoning_depth (0-3)
- Phase defaults: baseline=15%, finetuned=50%, deployment=85%

**What's unclear:**
- How to map reasoning_depth (0-3) + hallucination_detected (bool) to pass/fail threshold?
- Should hallucination be absolute gate (auto-fail) or weighted dimension?

**Recommendation:**
- Hallucination is absolute gate: `if hallucination_detected: benchmark_score = 0`
- Reasoning depth maps to 0-1: `reasoning_depth / 3.0`
- Threshold applies to final score: `benchmark_score >= threshold`
- Example: reasoning_depth=3, hallucination_detected=False → score=1.0 (pass all thresholds)
- Example: reasoning_depth=3, hallucination_detected=True → score=0.0 (fail all thresholds)

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Claim extraction from text | Custom sentence splitter with NER | LLM-based claim extraction in judge prompt | Handles complex compliance sentences, implicit claims |
| Semantic similarity for hallucination | Custom embedding + cosine similarity | RAGAs faithfulness metric (LLM-based NLI) | RLHF models defeat embedding checks ([ArXiv FACTUM](https://arxiv.org/pdf/2601.05866)) |
| Multi-dimensional scoring aggregation | Custom weighted formula | RAGAs evaluate() with built-in metrics | Handles metric dependencies, normalization, error cases |
| Judge prompt templates | String concatenation | Structured prompt with explicit CoT steps | Improves reliability 10-15%, provides debugging trail |

**Key insight:** Hallucination detection looks simple (check if claim in context) but requires semantic understanding, claim-level granularity, and handling of implicit inference. Use LLM-based verification, not custom heuristics.

## Architecture Patterns

### Recommended Evaluation Flow

```
Test Case Evaluation:
├── Rule-based Scoring (B1-B6)
│   └── Fast deterministic checks → immediate scores
├── LLM Judge Scoring (B3, B7-B21)
│   ├── Shadow Retrieval (if LLM-only mode)
│   ├── Single Judge Call (combined prompt)
│   │   ├── Claim extraction
│   │   ├── Hallucination check (vs contexts)
│   │   └── Reasoning depth assessment
│   └── Output: {reasoning_depth: 0-3, hallucination_detected: bool}
└── RAGAs Scoring (all test cases)
    ├── Base metrics (factual_recall, answer_relevancy, semantic_similarity)
    └── Context metrics (context_faithfulness, context_precision, context_recall) [RAG only]

Final Scores:
├── Benchmark Score (rule-based OR LLM judge)
│   └── LLM Judge: if hallucination_detected: 0.0 else: reasoning_depth/3.0
└── RAGAs Score (independent, diagnostic)
    └── (factual_recall + answer_relevancy + semantic_similarity)/3
```

### Multi-Layered Pipeline Pattern

```
Evaluation Pipeline Layers:
1. Deterministic Triage (B1-B6)
   - Fast filtering for objective metrics
   - Label matching, citation extraction, keyword detection
   - Output: immediate pass/fail or score

2. LLM Judge Semantic Evaluation (B3, B7-B21)
   - Escalated from triage (cannot assess with rules)
   - Reasoning depth + hallucination detection
   - Output: 0-3 score + binary flag + justification

3. RAGAs Quality Assessment (all cases)
   - Generic quality dimensions
   - Independent from benchmark scoring
   - Output: 7 metric scores (diagnostic)

4. Aggregation & Reporting
   - Benchmark Score (primary)
   - RAGAs Score (diagnostic)
   - Per-dimension breakdown
   - Hallucination flags for tracking
```
