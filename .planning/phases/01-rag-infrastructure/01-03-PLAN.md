<objective>
Build the LangGraph adaptive RAG graph with all nodes (query analysis, retrieval, grading, generation, fallback) and conditional routing edges.

Purpose: This is the core intelligence of the RAG system. The adaptive graph pattern handles the 40-60% failure rate of naive RAG by implementing self-correction loops, relevance grading, and graceful fallback. Every node is a composable function wired through LangGraph's StateGraph.

Output: A compiled LangGraph graph that accepts a query string and returns a response with retrieved context, grading scores, and RAG-augmented or model-only indication.
</objective>

       - Define `GraphState(TypedDict)` with fields:
         * `query` (str): Original user query
         * `rewritten_query` (str): Query optimized for retrieval
         * `needs_retrieval` (bool): Whether query requires document retrieval
         * `documents` (list): Retrieved LangChain Document objects
         * `filtered_documents` (list): Documents that passed grading
         * `grading_scores` (list[float]): Per-document relevance scores
         * `retrieval_succeeded` (bool): Whether relevant documents were found
         * `retrieval_attempts` (int): Number of retrieval attempts (for loop detection)
         * `generation` (str): Generated response text
         * `is_rag_augmented` (bool): Whether response used RAG context

    3. Create `src/retrieval/nodes/query_analysis.py`:
       - Function `analyze_query(state: GraphState) -> GraphState` that:
         * Uses Llama-Primus-Reasoning via ChatOllama with structured output (Pydantic model)
         * Binary classification: `needs_retrieval` (True/False)
         * Also produces `rewritten_query` optimized for vector search (expand acronyms, add context)
         * Prompt: System message explaining CCoP compliance context, asking if query needs document retrieval or is a general question
         * Sets `state["needs_retrieval"]` and `state["rewritten_query"]`
         * If LLM call fails, default to `needs_retrieval=True` (safer — attempt retrieval)
       - IMPORTANT: Use `ChatOllama(model="primus-reasoning")` from langchain_community — model name from Settings, not hardcoded
       - Start with binary classification as recommended by research (Pitfall 2: don't over-engineer)

    4. Create `src/retrieval/nodes/retrieval.py`:
       - Function `retrieve_documents(state: GraphState) -> GraphState` that:
         * Uses `DatabricksVectorSearch` from `databricks_langchain` as retriever
         * Queries with `state["rewritten_query"]`, k=20
         * Retrieves metadata columns: document_source, section, clause, citation_id, document_type
         * Sets `state["documents"]` with retrieved Document objects
         * Increments `state["retrieval_attempts"]`
         * Logs query, result count, and top 3 document sources
       - Retriever configuration:
         * `text_column="text"`
         * `columns=["document_source", "section", "subsection", "clause", "citation_id", "document_type"]`
       - The retriever should be created once and reused (not per-query) — pass via closure or module-level initialization
       - Configuration (endpoint, index name, etc.) from Settings, NOT hardcoded

    5. Create `src/retrieval/nodes/grading.py`:
       - Function `grade_documents(state: GraphState) -> GraphState` that:
         * Grades each document in `state["documents"]` for relevance to query
         * Uses LLM-as-judge pattern: Llama-Primus-Reasoning with structured output
         * Pydantic model `GradeResult`: score (float 0-1), reasoning (str)
         * Prompt: "Grade relevance of this CCoP clause to the user question. Score 0-1."
         * Filters documents: keep only those with score > 0.6 (relevance threshold from research)
         * Sets `state["filtered_documents"]`, `state["grading_scores"]`, `state["retrieval_succeeded"]`
         * `retrieval_succeeded = len(filtered_documents) > 0`
         * Logs: total docs, filtered docs, scores
       - IMPORTANT: Grade ALL retrieved documents, not just top-k. The grading step IS the re-ranking.

    6. Create `src/retrieval/nodes/generation.py`:
       - Function `generate_response(state: GraphState) -> GraphState` that:
         * Uses Llama-Primus-Reasoning via ChatOllama
         * Constructs prompt with:
           - System message: "You are a CCoP 2.0 compliance expert. Answer using the retrieved context. Include citation anchors <c>citation_id</c> for each source used."
           - Retrieved context: formatted from `state["filtered_documents"]` with citation_id anchors
           - User query: `state["query"]`
         * Sets `state["generation"]` with response text
         * Sets `state["is_rag_augmented"] = True`
         * Extracts initial citations from document metadata
         * Logs: query, response length, document count used
       - Context formatting: Each document formatted as:
         ```
         [Source: <c>{citation_id}</c>]
         {document text}
         ```

    7. Create `src/retrieval/nodes/fallback.py`:
       - Function `fallback_generation(state: GraphState) -> GraphState` that:
         * Generates response WITHOUT retrieved context
         * System message: "You are a CCoP 2.0 compliance expert. Answer based on your training knowledge. Note: This response is NOT grounded in specific CCoP document retrieval."
         * Sets `state["generation"]` with response
         * Sets `state["is_rag_augmented"] = False`
         * Sets `state["citations"] = []`
         * LOGS the failure: query, retrieval_attempts, grading_scores (this feeds Phase 2 gap analysis)
         * Log format: `{"event": "retrieval_fallback", "query": ..., "attempts": ..., "grading_scores": ..., "reason": "no_relevant_documents"}`

    AVOID: Do NOT use ChatOpenAI — use ChatOllama for local Llama-Primus-Reasoning inference.
    AVOID: Do NOT store full document content in state unnecessarily — store Document objects (LangChain handles serialization).
    AVOID: Do NOT implement complex multi-class query routing — binary classification only (Pitfall 2).
    WHY LLM-as-judge for grading: Research shows this catches silent failures (Pitfall 1) where vector search returns irrelevant results but system appears to work.

    1. Create `src/retrieval/edges/__init__.py` (empty)

    2. Create `src/retrieval/edges/routing.py`:
       - Function `route_query(state: GraphState) -> str` that:
         * Returns "retrieval" if `state["needs_retrieval"]` is True
         * Returns "fallback" if False
         * This is the first routing decision after query analysis

       - Function `decide_after_grading(state: GraphState) -> str` that:
         * If `state["retrieval_succeeded"]` is True: return "generate"
         * If `state["retrieval_attempts"]` >= 3: return "fallback" (max retry budget, prevents infinite loops — Pitfall from research)
         * Otherwise: return "rewrite" (trigger self-correction loop — rewrite query and retry)
         * Logs the decision and reasoning

       - Function `rewrite_query(state: GraphState) -> GraphState` that:
         * Uses LLM to rewrite the query for better retrieval
         * Prompt: "The following query did not retrieve relevant CCoP documents. Rewrite it to improve retrieval: {original_query}. Previous rewritten query: {rewritten_query}"
         * Updates `state["rewritten_query"]`
         * This function acts as BOTH an edge decision AND a mini-node (query rewriting)
         * Actually, make this a separate node (cleaner) — add it to the graph as "rewrite_query" node

    3. Create `src/retrieval/graph.py`:
       - Function `build_rag_graph(settings: Settings) -> CompiledGraph` that:
         * Creates `StateGraph(GraphState)`
         * Adds nodes:
           - "query_analysis" -> analyze_query
           - "retrieval" -> retrieve_documents
           - "grade_documents" -> grade_documents
           - "rewrite_query" -> rewrite_query (self-correction node)
           - "generate" -> generate_response
           - "fallback" -> fallback_generation
         * Sets entry point: "query_analysis"
         * Adds edges:
           - query_analysis -> conditional: route_query -> {"retrieval": "retrieval", "fallback": "fallback"}
           - retrieval -> grade_documents
           - grade_documents -> conditional: decide_after_grading -> {"generate": "generate", "rewrite": "rewrite_query", "fallback": "fallback"}
           - rewrite_query -> retrieval (loop back)
           - generate -> END
           - fallback -> END
         * Compiles and returns the graph
         * The graph should be configurable (settings for model name, retrieval params, etc.)

       - Function `create_rag_pipeline(settings: Settings) -> callable` that:
         * Builds the graph via build_rag_graph
         * Returns a simple callable: `def query(question: str) -> dict` that:
           - Creates initial state: `{"query": question, "retrieval_attempts": 0}`
           - Invokes the compiled graph
           - Returns the final state (with generation, citations, is_rag_augmented, etc.)
         * This is the public API for the RAG pipeline

       Graph topology:
       ```
       query_analysis
           |
       [needs_retrieval?]
          / \
         Y   N
         |    \
       retrieval  fallback -> END
         |
       grade_documents
         |
       [relevant docs found?]
        / | \
       Y  retry  N (max attempts)
       |    |      \
     generate  rewrite_query  fallback -> END
       |         |
       END    retrieval (loop)
       ```

    AVOID: Do NOT add more than 3 retrieval retry loops (prevents infinite loops — bounded self-correction).
    AVOID: Do NOT use checkpointing/persistence for the graph state — in-memory execution is sufficient for this use case.
    WHY separate rewrite_query node: Cleaner than embedding rewrite logic in an edge function. LangGraph best practice is nodes for state mutations, edges for routing decisions.
  </action>
