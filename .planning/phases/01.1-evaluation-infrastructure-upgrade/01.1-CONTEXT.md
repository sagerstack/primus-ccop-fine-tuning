# Phase 1.1: Evaluation Infrastructure Upgrade - Context

**Gathered:** 2026-02-13
**Updated:** 2026-03-14
**Status:** Ready for planning

<domain>
## Phase Boundary

Upgrade evaluation scoring methodology with two complementary layers: (1) LLM-as-Judge rubrics for 15 benchmarks replacing semantic similarity proxies, and (2) RAGAs metrics for RAG pipeline quality evaluation. The 6 rule-based benchmarks (B1, B2, B4, B5, B6, B21) remain unchanged. Infrastructure concerns (ModelGateway, MLflow tracking, CLI flags, evaluation runs) are deferred to a subsequent phase.

</domain>

<decisions>
## Implementation Decisions

### Eval Framework Architecture
- Scoring happens in the **application layer**, not inside LangGraph
- Flow: `EvaluateModelsUseCase` calls `IModelGateway.generate()` -> gets response -> calls `ScoringService.score()` -> creates `EvaluationResult`
- LangGraph graph has **no scoring node** -- it only handles routing, retrieval, and generation
- `IModelGateway` stays pure -- only generates responses, no scoring concern
- ScoringService lives in the domain layer, calls LLMJudgeService for LLM-as-Judge benchmarks

### Two Scoring Layers
- **Layer 1: Benchmark scoring (21 benchmarks)** -- domain-specific compliance quality ("Is this a good CCoP compliance answer?")
  - 6 rule-based (B1, B2, B4, B5, B6, B21) -- unchanged
  - 15 LLM-as-Judge (B3, B7-B20) -- via LLMJudgeService with benchmark-specific rubrics
- **Layer 2: RAGAs metrics** -- generic response and retrieval quality
  - For all responses: answer_correctness, answer_relevancy
  - For RAG responses only: faithfulness, context_precision, context_recall, context_relevancy
- Both layers produce separate scores per test case -- not merged into a single score
- Richer analysis: a response can score high on RAGAs (factually correct) but low on benchmarks (poor compliance reasoning), or vice versa

### LLM Judge Design
- Judge LLM: **Claude Sonnet via Claude Agent SDK** (subprocess `claude chat`) -- same as current implementation
- Scoring scale: **0-3 anchored** (aligned with criteria-establishment.md): 0=Incorrect, 1=Partial, 2=Complete, 3=Exceeds. Normalized to 0-1 for aggregation
- Judge error handling: **Skip and flag** -- on failure, mark test case as `judge_error` with no score. No fallback scores. Missing data > wrong data
- Evaluation dimensions: **Benchmark-specific** -- each of the 15 LLM-judged benchmarks gets its own dimensions from criteria-establishment.md (not a shared generic set)
- JudgeEvaluation data model: **Dynamic dimensions** -- list of (dimension_name, score, weight) tuples instead of fixed fields

### RAGAs Integration
- RAGAs evaluator LLM: **Claude Sonnet via LangchainLLMWrapper(ChatAnthropic)** -- uses ragas library's native LLM wrapper
- Architecture: **Separate RagasEvaluationService** in domain layer -- independent from ScoringService. ScoringService handles benchmarks, RagasEvaluationService handles RAG quality metrics
- Metrics for LLM-only responses: answer_correctness, answer_relevancy (no retrieval context needed)
- Metrics for hybrid/RAG responses: all above + faithfulness, context_precision, context_recall, context_relevancy
- RAGAs needs: question, retrieved contexts (from GraphState.documents), generated answer, ground truth (from test case expected_response/key_facts/clause_reference)
- Mechanical retrieval scores (similarity scores, reranker scores, retrieval attempts) already captured in GraphState -- RAGAs adds quality judgment on top

### RAGAs Pipeline Wiring
- RagasEvaluationService is **wired into EvaluateModelUseCase** alongside ScoringService -- called per test case
- RAGAs evaluation results stored as **separate field** on EvaluationResult (`ragas_evaluation`) -- not mixed with benchmark metrics
- RAGAs metrics do **NOT affect** overall_score or pass/fail determination -- those use benchmark metrics only
- RagasEvaluationService injected via DI container with **conditional activation** -- `ragas_enabled` setting controls whether RAGAs runs
- Current ModelGateway returns ModelResponse without retrieved contexts -- RAGAs evaluates with `retrieved_contexts=None` (answer_correctness, answer_relevancy only). Context metrics (faithfulness, context_precision, context_recall) activate when ModelGateway is upgraded to expose GraphState documents (deferred phase)
- JSON result serialization includes RAGAs as a **separate section** per test result

### Scoring Migration Strategy
- **Replace entirely** -- remove `_score_reasoning_track` (semantic similarity) for B8, B9, B11, B15, B17, B18, B19. Remove `_score_b3_hallucination` misuse for B3. Implement new LLM judge scorers for B7, B10, B14, B16. Upgrade B12, B13, B20 rubrics
- SemanticSimilarityService can be removed after migration (no longer used by any scorer)
- Old results: **Keep 49.2% as historical** AND re-run 118 cases through new scoring to get a restated baseline under new methodology

### Claude's Discretion
- Rubric prompt structure for each of the 15 LLM-judged benchmarks (based on criteria-establishment.md anchors)
- RAGAs library integration approach (ragas package vs custom implementation)
- RAGAs LLM wrapper implementation for Claude subprocess
- Error handling and logging detail level

</decisions>

<specifics>
## Specific Ideas

- Evaluation rubrics should be derived from `docs/phase-2/criteria-establishment.md` anchored 0-3 scale -- each benchmark has specific anchors with CCoP-specific examples at each level
- The Component 4 document (`docs/phase-2/evaluation-rubrics.md`) should be created during this phase to formalize all 15 rubric prompts before implementation
- Benchmark categorization: 6 rule-based (B1, B2, B4, B5, B6, B21) + 15 LLM-as-Judge (B3, B7-B20) -- all 21 benchmarks scoreable in a single automated run with no human/expert dependencies

</specifics>

</deferred>
