**Part A: Update IModelGateway interface**

Add `mode` parameter to `generate_response` in `src/application/ports/output/i_model_gateway.py`:

```python
@abstractmethod
async def generate_response(
    self,
    prompt: str,
    model_name: str,
    temperature: float = 0.7,
    max_tokens: int = 1024,
    top_p: float = 0.9,
    top_k: int = 40,
    system_prompt: Optional[str] = None,
    metadata: Optional[Dict[str, any]] = None,
    mode: str = "llm-only",  # NEW: pipeline routing mode
) -> ModelResponse:
```

Default to "llm-only" for backward compatibility — existing OllamaGateway callers don't need to change. The `mode` parameter controls LangGraph path: "hybrid" (retrieval + generation), "llm-only" (fallback node only), "rag-only" (retrieval + raw context).

Also update OllamaGateway in `src/infrastructure/adapters/models/ollama_gateway.py` to accept `mode` parameter (ignore it — Ollama always does direct inference). Add `mode: str = "llm-only"` to its generate_response signature and add a log warning if mode != "llm-only": `self._logger.warning("OllamaGateway ignores mode parameter, always uses direct inference")`.

**Part B: Create ModelGateway adapter**

Create `src/infrastructure/adapters/models/model_gateway.py`:

ModelGateway implements IModelGateway and wraps LangGraph's `create_rag_pipeline` callable. Follow the pattern from RESEARCH.md Pattern 3, with these specifics:

1. Constructor takes `settings` (for create_rag_pipeline) and `logger`. Lazily initialize pipeline on first call (same pattern as LangGraphRagAdapter).

2. `generate_response` implementation:
   - Call `self._pipeline(prompt, mode=mode)` to invoke LangGraph
   - Extract `generation` from final state
   - Map to ModelResponse entity with metadata including mode, is_rag_augmented, retrieval_attempts, citations
   - If mode is "hybrid" and final_state["is_rag_augmented"] is False, log a warning (Pitfall 5 mitigation from research)
   - On pipeline error, raise the error directly — do NOT catch and fallback. Phase context decision: "RAG unavailability: Fail explicitly"
   - model_name comes from the settings (the underlying Ollama model), not from the caller's model_name param

3. `is_model_available` implementation:
   - Ensure pipeline initialized
   - For "llm-only" mode: check Ollama availability via settings.ollama_host
   - For "hybrid"/"rag-only" modes: also check Databricks config (settings.databricks_host, databricks_token, databricks_catalog)
   - Do NOT run a test query for health check — just check config presence

4. `list_available_models` — return the model name from settings

5. `get_model_info` — return gateway_type, supported modes, model name

**What to avoid and WHY:**
- Do NOT implement automatic fallback from hybrid to llm-only — this masks RAG issues and produces misleading results (Pitfall 5).
- Do NOT eagerly initialize pipeline in constructor — Databricks may not be configured, and llm-only mode doesn't need it. Use lazy init same as LangGraphRagAdapter.
- Do NOT remove OllamaGateway — it's still needed for direct Ollama access outside evaluation context. Just keep it as an alternative adapter.
- Do NOT hardcode model name — read from settings.
