# Phase 1.1: Evaluation Infrastructure Upgrade - Research

**Researched:** 2026-02-13
**Domain:** LLM evaluation infrastructure, experiment tracking, LLM-as-Judge methodology
**Confidence:** HIGH

## Summary

This phase requires upgrading evaluation infrastructure across three major domains: (1) replacing semantic similarity scoring with LLM-as-Judge rubrics for 15 benchmarks using anchored 0-3 scales, (2) unifying model queries through a single ModelGateway that wraps the existing LangGraph pipeline with mode-based routing, and (3) integrating MLflow experiment tracking with Databricks for comparative evaluation runs.

The standard approach for LLM-as-Judge evaluation in 2026 uses structured rubrics with clear anchors, Chain-of-Thought prompting, and 0-3 or 0-4 discrete scales to reduce bias. MLflow 3.x provides mature experiment tracking with Databricks integration requiring minimal configuration. LangGraph's conditional edges pattern supports mode-based routing through path maps or type hints, allowing hybrid/llm-only/rag-only execution paths.

The existing codebase already has LLM-as-Judge infrastructure (Claude Agent SDK via subprocess), LangGraph routing logic (route_by_mode), and domain entities. The upgrade path is: (1) create 15 benchmark-specific rubric prompts from criteria-establishment.md anchors, (2) extend IModelGateway interface to accept mode parameter and wrap LangGraph invocation, (3) add MLflow logging calls to EvaluateModelsUseCase with --track flag gating.

**Primary recommendation:** Use structured rubric templates with dimension-specific 0-3 anchors per benchmark (not generic prompts), add mlflow ^3.9.0 to dependencies, and implement ModelGateway as a thin adapter over LangGraph's existing create_rag_pipeline callable.

## Architecture Patterns

### Pattern 1: MLflow Run Lifecycle with Context Manager
**What:** Wrap evaluation runs in mlflow.start_run() context to automatically manage lifecycle and ensure proper resource cleanup.

**When to use:** Every evaluation invocation when --track flag is enabled.

**Example:**
```python
# Source: https://mlflow.org/docs/latest/ml/tracking/
import mlflow

def evaluate_with_tracking(test_cases, model_gateway, mode):
    mlflow.set_experiment("CCoP Evaluation")

    with mlflow.start_run(run_name=f"{model_name}_{mode}_{timestamp}"):
        # Log parameters
        mlflow.log_param("model", model_name)
        mlflow.log_param("mode", mode)
        mlflow.log_param("benchmark_count", len(test_cases))

        # Run evaluation
        results = run_evaluation(test_cases, model_gateway, mode)

        # Log metrics
        mlflow.log_metric("overall_accuracy", results.overall_score)
        mlflow.log_metric("hallucination_rate", results.hallucination_rate)

        # Log artifacts
        mlflow.log_artifact("results.json")

    return results
```

### Pattern 2: LLM-as-Judge with Anchored Rubric Prompts
**What:** Structure judge prompts with (1) dimension definitions from criteria-establishment.md, (2) explicit 0-3 anchors with CCoP-specific examples, (3) Chain-of-Thought instructions, (4) JSON response format.

**When to use:** All 15 LLM-judged benchmarks (B3, B7-B20).

**Example:**
```python
# Source: Research synthesis from LalaEval + 2026 best practices
def build_judge_prompt_b8_gap_prioritization(test_case, response):
    return f"""You are an expert CCoP 2.0 compliance auditor evaluating gap prioritization quality.

**Test Question:**
{test_case.question}

**Model Response:**
{response.content}

**Expected Answer:**
{test_case.expected_response}

**Evaluation Dimension: Gap Prioritization (B8)**

Score the response on a 0-3 anchored scale:

**0 (Incorrect):** No prioritization logic or reversed priorities
- Example: Lists gaps alphabetically; prioritizes cosmetic issue over critical MFA gap

**1 (Partial):** Prioritization attempted but criteria unclear or inconsistent
- Example: "Fix MFA first because it's important" without risk-based reasoning

**2 (Complete):** Risk-based prioritization with clear criteria (likelihood × impact)
- Example: "Priority 1: MFA (critical — remote access is primary attack vector, direct essential service impact). Priority 2: Segmentation (high — limits blast radius). Priority 3: Logging (medium — detective, not preventive)"

**3 (Exceeds):** Risk-based plus implementation sequencing and quick-win identification
- Example: Complete reasoning plus "Quick win: MFA can be deployed in 2 weeks with existing IAM. Strategic: segmentation requires network redesign — start architecture review now, implement in phases"

**Instructions:**
1. Think step-by-step about the response quality (Chain-of-Thought)
2. Identify which anchor level (0-3) best matches the response
3. Provide your evaluation in JSON format:

{{
  "dimension": "gap_prioritization",
  "score": <0-3>,
  "weight": 1.0,
  "justification": "<2-3 sentence explanation citing specific evidence>",
  "confidence": <0.0-1.0>
}}

Only return the JSON, nothing else."""
```

### Pattern 3: ModelGateway as LangGraph Wrapper
**What:** Implement ModelGateway as thin adapter that delegates to LangGraph's create_rag_pipeline callable, extracts generation from final state, and maps to ModelResponse entity.

**When to use:** All model inference calls in evaluation pipeline.

**Example:**
```python
# Source: Existing graph.py + IModelGateway interface
class ModelGateway(IModelGateway):
    """LangGraph pipeline wrapper implementing IModelGateway."""

    def __init__(self, settings, logger):
        self._pipeline = create_rag_pipeline(settings)
        self._logger = logger

    async def generate_response(
        self,
        prompt: str,
        model_name: str,
        mode: str = "hybrid",  # NEW: mode parameter
        temperature: float = 0.7,
        max_tokens: int = 1024,
        **kwargs
    ) -> ModelResponse:
        """Generate response through LangGraph pipeline."""
        start_time = datetime.utcnow()

        try:
            # Invoke LangGraph pipeline with mode routing
            final_state = self._pipeline(prompt, mode=mode)

            end_time = datetime.utcnow()

            return ModelResponse(
                response_id=uuid4(),
                content=final_state["generation"],
                model_name=model_name,
                tokens_used=0,  # LangGraph doesn't expose token count
                latency_ms=int((end_time - start_time).total_seconds() * 1000),
                temperature=temperature,
                created_at=end_time,
                metadata={
                    "mode": mode,
                    "is_rag_augmented": final_state.get("is_rag_augmented", False),
                    "retrieval_attempts": final_state.get("retrieval_attempts", 0),
                    "citations": final_state.get("citations", []),
                }
            )
        except Exception as e:
            self._logger.error(f"Pipeline invocation failed: {e}", mode=mode)
            raise
```

### Anti-Patterns to Avoid

- **Generic LLM-as-Judge prompts:** Don't use one-size-fits-all rubrics. Each benchmark needs specific anchors from criteria-establishment.md with CCoP-specific examples at each level (0-3). Generic prompts cause score inflation and low inter-judge reliability.

- **Semantic similarity for reasoning quality:** Don't use sentence embeddings to score gap prioritization, risk justification, or audit perspective. Similarity measures word overlap, not reasoning quality. A response can be semantically similar to expected answer but have reversed priorities or circular logic.

- **Silent mode fallback:** Don't fall back from hybrid to llm-only when Databricks unavailable. Fail explicitly with clear error. Silent fallbacks mask RAG issues and produce misleading comparison results.

- **MLflow logging without experiment context:** Don't call mlflow.log_param/metric without setting experiment first. Logs go to default experiment, making runs unsearchable. Always mlflow.set_experiment() before start_run().

- **Hardcoded rubric prompts:** Don't hardcode 0-3 anchor text in Python strings. Create docs/phase-2/evaluation-rubrics.md with formalized rubrics as Component 4, then load at runtime. Rubrics will evolve; code should reference, not embed.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Experiment tracking and comparison | Custom JSON logging + manual diffing | MLflow Tracking API | MLflow handles run comparison UI, metric visualization, artifact storage, and query API. Custom solutions miss decades of ML tooling evolution and create vendor lock-in to homegrown format. |
| LLM response scoring | Custom regex + keyword matching for rubric levels | LLM-as-Judge with structured prompts | Keyword matching can't evaluate reasoning quality, proportionality, or logical coherence. Claude judge with CoT prompting achieves 80%+ agreement with human experts (Databricks 2026 research). |
| Conditional graph routing | If/else chains with manual state passing | LangGraph add_conditional_edges | LangGraph provides state management, cycle detection, parallel execution, and rendering. Manual routing recreates graph theory primitives poorly and breaks when adding nodes. |
| 0-3 score normalization | Manual division scattered across scorers | Centralized EvaluationMetric factory | Normalization logic (score/3.0) appears 15+ times if hand-rolled per benchmark. Single factory function ensures consistency and makes scale changes (e.g., 0-4) a one-line edit. |

**Key insight:** LLM evaluation infrastructure matured significantly in 2024-2026. Standards emerged: anchored discrete scales over continuous, CoT prompting over direct scoring, MLflow over custom logging, structured rubrics over generic. Don't rebuild solved problems; compose proven libraries.

## Common Pitfalls

### Pitfall 1: Position Bias in LLM-as-Judge
**What goes wrong:** Judge LLM scores first option higher ~40% of the time regardless of quality (GPT-4 research). When comparing expected vs actual response order affects score.

**Why it happens:** LLMs exhibit recency and primacy bias. Seeing expected answer first anchors evaluation; seeing model response first creates leniency.

**How to avoid:**
- Use single-output scoring with rubric (current design), not pairwise comparison
- Don't show expected answer if using pairwise mode
- For absolute scoring, provide expected answer as reference but don't ask "which is better"
- Current prompt structure (question → response → expected → rubric) is correct pattern

**Warning signs:** Scores consistently higher when expected answer appears first in prompt. Inter-judge reliability drops when prompt order changes.

### Pitfall 2: Continuous Scale Score Inflation
**What goes wrong:** Using 0.0-1.0 continuous scale causes central tendency bias. Judges avoid extremes (0.0, 1.0) and cluster around 0.6-0.8, making all responses look mediocre.

**Why it happens:** Without clear anchors, evaluators default to "middle is safe." Lack of concrete examples at each level leads to inconsistent interpretation.

**How to avoid:**
- Use discrete 0-3 scale with explicit anchors (criteria-establishment.md design)
- Provide CCoP-specific examples at EACH level (not just 0 and 3)
- Normalize to 0-1 only for aggregation: score/3.0
- Research shows 0-3 or 0-4 scales have higher inter-rater reliability than 0-1 continuous

**Warning signs:** All benchmark scores cluster in 0.5-0.7 range. Standard deviation < 0.15 across diverse test cases. Judge frequently assigns same score (e.g., 0.6) to clearly different quality levels.

### Pitfall 3: Judge Evaluation Without CoT
**What goes wrong:** Direct scoring prompts ("Rate this 0-3") produce inconsistent scores and poor alignment with human judgment.

**Why it happens:** Judge LLM doesn't show reasoning, making errors opaque. Without explicit reasoning step, model takes shortcuts and misses nuance.

**How to avoid:**
- Add Chain-of-Thought instruction: "Think step-by-step about the response quality"
- Request justification field in JSON response (2-3 sentence explanation)
- Optionally: request dimension-specific reasoning before overall score
- CoT improves reliability by 10-15% (2026 research)

**Warning signs:** Judge scores are unpredictable. Same test case gets different scores on re-runs. Justification field is generic or doesn't cite specific evidence from response.

### Pitfall 4: MLflow Run Collision
**What goes wrong:** Multiple evaluation runs execute concurrently, create nested runs, or overwrite each other's metrics.

**Why it happens:** mlflow.start_run() without context manager doesn't auto-close. Nested start_run() calls create parent-child hierarchy. Concurrent runs to same experiment can collide.

**How to avoid:**
- Always use with mlflow.start_run() context manager (auto-closes on exit)
- For parallel evaluation (e.g., batch mode), use run_id to separate runs or sequential execution
- Set unique run_name: f"{model}_{mode}_{timestamp}" to distinguish runs
- Don't nest start_run() calls; child runs confuse comparison UI

**Warning signs:** MLflow UI shows runs with identical timestamps. Metrics logged to wrong run. RunNotFoundError or ActiveRunConflict exceptions.

### Pitfall 5: Mode Routing Without Databricks Health Check
**What goes wrong:** Evaluation starts with mode=hybrid, Databricks is down, pipeline silently falls back to llm-only, results mislabeled as "RAG-augmented."

**Why it happens:** Graceful degradation is good for production UX but bad for evaluation reproducibility. Phase context requires explicit failure when RAG unavailable.

**How to avoid:**
- Add Databricks health check before evaluation run if mode=hybrid or rag-only
- Fail fast with clear error: "Databricks Vector Search unavailable. Cannot run hybrid mode evaluation."
- Don't implement automatic fallback in evaluation context (different from production query context)
- Log mode to MLflow params AND verify final_state["is_rag_augmented"] matches expected mode

**Warning signs:** hybrid mode evaluation completes when Databricks is down. is_rag_augmented=False for all test cases in hybrid run. Retrieval_attempts=0 when mode=hybrid.

### Pitfall 6: Rubric Drift from Criteria Document
**What goes wrong:** Rubric prompts diverge from criteria-establishment.md over time. Developer tweaks anchor examples in code without updating source document. Evaluation becomes inconsistent.

**Why it happens:** Rubrics embedded as Python f-strings are easy to edit inline. No forcing function to sync with criteria-establishment.md.

**How to avoid:**
- Create docs/phase-2/evaluation-rubrics.md (Component 4) during this phase
- Store full rubric prompts in rubrics.md, reference from code
- Add validation: compare rubric hash against criteria-establishment.md on startup
- Document sync process: criteria → rubrics.md → code (one-way flow)

**Warning signs:** Code comments say "see criteria-establishment.md" but prompt text doesn't match. Different developers use different anchor examples for same benchmark. Test case scores change after minor prompt "clarifications."

```python
# Source: MLflow Tracking API + phase requirements
import mlflow
from datetime import datetime

class EvaluateModelsUseCase:
    def __init__(self, model_gateway, scoring_service, logger, enable_tracking=False):
        self._model_gateway = model_gateway
        self._scoring_service = scoring_service
        self._logger = logger
        self._enable_tracking = enable_tracking

    def execute(self, test_cases, model_name, mode="hybrid"):
        """Execute evaluation with optional MLflow tracking."""

        if self._enable_tracking:
            # Configure Databricks MLflow
            mlflow.set_experiment("/Shared/CCoP_Evaluation")

            # Create unique run name
            timestamp = datetime.utcnow().strftime("%Y%m%d_%H%M%S")
            run_name = f"{model_name}_{mode}_{timestamp}"

            with mlflow.start_run(run_name=run_name):
                # Log parameters
                mlflow.log_param("model", model_name)
                mlflow.log_param("mode", mode)
                mlflow.log_param("test_case_count", len(test_cases))
                mlflow.log_param("benchmark_version", "phase2_anchored_0_3")

                # Run evaluation
                results = self._run_evaluation(test_cases, model_name, mode)

                # Log overall metrics
                mlflow.log_metric("overall_accuracy", results.overall_score)
                mlflow.log_metric("hallucination_rate", results.hallucination_rate)

                # Log per-benchmark scores
                for benchmark, score in results.per_benchmark_scores.items():
                    mlflow.log_metric(f"benchmark_{benchmark}", score)

                # Log artifacts
                results_json = results.to_json()
                with open("evaluation_results.json", "w") as f:
                    f.write(results_json)
                mlflow.log_artifact("evaluation_results.json")

                return results
        else:
            # Non-tracked evaluation
            return self._run_evaluation(test_cases, model_name, mode)
```

```python
def build_judge_prompt(benchmark_type, test_case, response):
    """Build rubric prompt from criteria-establishment.md anchors."""

    # Load rubric template for this benchmark
    rubric = get_rubric_template(benchmark_type)  # From evaluation-rubrics.md

{rubric.dimension_definitions}

2. For each dimension, identify which anchor level (0-3) best matches
3. Provide evaluation in JSON format:

{{
  "dimensions": [
    {{"dimension": "<name>", "score": <0-3>, "weight": <float>}},
    ...
  ],
  "justification": "<2-3 sentence explanation citing specific evidence>",
  "confidence": <0.0-1.0>
}}

Only return the JSON, nothing else."""

    return base_prompt

# Example rubric template structure (loaded from evaluation-rubrics.md)
class RubricTemplate:
    def __init__(self, benchmark_type):
        self.benchmark_type = benchmark_type
        self.dimensions = []  # [(name, weight, anchors)]

    @property
    def dimension_definitions(self):
        """Format dimension anchors for prompt."""
        sections = []
        for name, weight, anchors in self.dimensions:
            section = f"**Dimension: {name} (weight: {weight})**\n\n"
            for level, anchor in anchors.items():
                section += f"**{level}:** {anchor.definition}\n"
                section += f"- Example: {anchor.example}\n\n"
            sections.append(section)
        return "\n".join(sections)
```

### Example 3: LangGraph Pipeline Wrapper as ModelGateway
```python
# Source: Existing graph.py create_rag_pipeline + IModelGateway interface
from rag.retrieval.graph import create_rag_pipeline
from application.ports.output.i_model_gateway import IModelGateway
from domain.entities.model_response import ModelResponse
from datetime import datetime
from uuid import uuid4

class ModelGateway(IModelGateway):
    """LangGraph RAG pipeline wrapped as IModelGateway."""

    def __init__(self, settings, logger):
        self._pipeline = create_rag_pipeline(settings)
        self._logger = logger
        self._model_name = "llama-primus-reasoning"  # From settings

    async def generate_response(
        self,
        prompt: str,
        model_name: str,
        mode: str = "hybrid",  # NEW: mode parameter for routing
        temperature: float = 0.7,
        max_tokens: int = 1024,
        top_p: float = 0.9,
        top_k: int = 40,
        system_prompt: str = None,
        metadata: dict = None,
    ) -> ModelResponse:
        """Generate response through LangGraph pipeline with mode routing."""
        start_time = datetime.utcnow()

        self._logger.info(f"Invoking LangGraph pipeline", mode=mode, prompt_length=len(prompt))

        try:
            # LangGraph pipeline invocation
            final_state = self._pipeline(prompt, mode=mode)

            end_time = datetime.utcnow()
            latency_ms = int((end_time - start_time).total_seconds() * 1000)

            # Extract generation from final state
            content = final_state.get("generation", "")

            # Verify mode consistency (Pitfall 5 mitigation)
            is_rag_augmented = final_state.get("is_rag_augmented", False)
            if mode == "hybrid" and not is_rag_augmented:
                self._logger.warning("Hybrid mode did not retrieve documents",
                                    retrieval_attempts=final_state.get("retrieval_attempts"))

            return ModelResponse(
                response_id=uuid4(),
                content=content,
                model_name=self._model_name,
                tokens_used=0,  # LangGraph doesn't expose token count
                latency_ms=latency_ms,
                temperature=temperature,
                created_at=end_time,
                metadata={
                    "mode": mode,
                    "is_rag_augmented": is_rag_augmented,
                    "retrieval_attempts": final_state.get("retrieval_attempts", 0),
                    "citations": final_state.get("citations", []),
                    "error": final_state.get("error", ""),
                    **(metadata or {})
                }
            )
        except Exception as e:
            self._logger.error(f"Pipeline invocation failed: {e}", mode=mode)
            # Don't fallback - fail explicitly per phase requirements
            raise

    async def is_model_available(self, model_name: str) -> bool:
        """Check if LangGraph pipeline is available."""
        # Health check: verify LangGraph can initialize and Databricks is reachable
        try:
            # Attempt minimal graph invocation
            test_state = self._pipeline("health check", mode="llm-only")
            return bool(test_state.get("generation"))
        except Exception:
            return False

    async def list_available_models(self) -> list[str]:
        """List models available through this gateway."""
        return [self._model_name]

    async def get_model_info(self, model_name: str) -> dict:
        """Get model information."""
        return {
            "name": self._model_name,
            "gateway_type": "langgraph_rag",
            "modes": ["hybrid", "llm-only", "rag-only"],
            "description": "Llama-Primus-Reasoning via LangGraph RAG pipeline"
        }
```

**Deprecated/outdated:**
- SemanticSimilarityService (sentence-transformers): Being removed in this phase. Replaced by LLM-as-Judge for reasoning benchmarks (B3, B7-B20). Semantic similarity remains valid for keyword matching (B4 terminology) but not reasoning quality.
- Fixed 3-dimension JudgeEvaluation: Replaced by dynamic dimensions list. Each benchmark has different dimensions per criteria-establishment.md (B8 has 1 dimension, B1 has 3 dimensions).
- Generic LLM-as-Judge rubrics: Replaced by benchmark-specific rubrics with CCoP-anchored examples. Generic prompts (e.g., "rate accuracy/completeness/alignment") cause score inflation and low reliability.

## Open Questions

1. **MLflow authentication for external clients**
   - What we know: Databricks notebooks auto-configure MLflow tracking URI. External clients need databricks-cli config or explicit token.
   - What's unclear: Does databricks-sdk (already in dependencies) provide auth that MLflow can reuse, or do we need separate databricks-cli setup?
   - Recommendation: Test MLflow connectivity in Databricks workspace first. If running externally, verify databricks-sdk auth token works with mlflow.set_tracking_uri("databricks").

2. **Rubric prompt token limits**
   - What we know: Benchmark-specific rubrics with 3+ dimensions and CCoP examples can exceed 1000 tokens. Claude Agent SDK has token limits.
   - What's unclear: Does Claude CLI subprocess support extended context (100k+ tokens), or do we need to truncate rubrics?
   - Recommendation: Test longest rubric (B1 with 3 dimensions) through Claude Agent SDK. If token limit hit, truncate test_case.expected_response (reference only) or split multi-dimension benchmarks into sequential judge calls.

3. **Per-benchmark vs per-dimension MLflow metrics**
   - What we know: 21 benchmarks, some with multiple dimensions. MLflow supports nested metrics.
   - What's unclear: Should we log mlflow.log_metric("benchmark_B1", 0.85) or mlflow.log_metric("B1_terminology", 0.9), mlflow.log_metric("B1_clause_interpretation", 0.8)?
