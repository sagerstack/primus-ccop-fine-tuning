# Phase 3.1: Eval Run Traceability & I/O Capture - Context

**Gathered:** 2026-04-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Every evaluation run gets a durable identity (`run_id`). Every per-case output captures enough input/output data — full composed prompt, retrieved contexts, prompt/completion/total token counts, latency — to debug a test case without re-running inference. Filename and directory layout are reorganised around `run_id` as the primary identifier.

Blocks the main baseline eval: running baseline without this phase produces results that cannot be debugged post-hoc.

In scope: run_id generation, JSON schema changes (v6), directory reorganisation, sidecar file for retrieved contexts, token/latency propagation, CLI verbose display of captured data, report-tooling rewire to glob per-run files.

Out of scope: retrieval quality, chunker fixes (Phase 3.2), ground truth corrections (Phase 3.3), new evaluation metrics, UI beyond CLI verbose output.

</domain>

<decisions>
## Implementation Decisions

### Run ID format

- Format: `eval-run-{mode}-{scope}-{yyyyMMdd}-{HHmm}`
- `mode` ∈ `{hybrid, llm-only, rag-only}` (matches existing `--mode` CLI flag)
- `scope` per encoding below
- Auto-generated at eval entry point; no `--run-id` CLI override
- Every invocation produces a fresh `run_id`; no resume logic for partial failures — a failed/interrupted run produces a partial result file with its own unique id

### Scope encoding

- Full suite (all benchmarks): `suite`
- Single benchmark (`--benchmarks B3`): `benchmark-B3`
- Multi-benchmark (`--benchmarks B1 --benchmarks B3 --benchmarks B7`): `benchmarks-B1-B3-B7` (sorted ascending, full IDs joined by hyphen)
- Tier (`--tier N`): `tier-{N}` (explicit, not expanded to benchmarks)
- Single test id (`--test-ids B3-001`): `test-B3-001` (reuses existing namespaced ID)
- Multi test-ids (`--test-ids B3-001 --test-ids B3-002`): `test-B3-001-B3-002` (same sorted-join pattern)
- Query (`ccop-eval query ask ...`): `query` — **new behavior**, every query persists a result JSON

### Filename and directory layout

- Per-run file: `{run_id}-{model}.json`
  - Example: `eval-run-hybrid-test-B3-001-20260421-1430-primus-reasoning.json`
- Contexts sidecar: `{run_id}-contexts.json` (same directory, same run_id prefix)
- Directory: `src/results/evaluations/{yyyy-MM}/` — nested by month (auto-archive as runs accumulate)
- Existing aggregated `{model}_results.json` file is **dropped** (no longer written)
- `ccop-eval report` tooling rewired to read per-run files via glob pattern over `evaluations/**/*-{model}.json`

### Captured payload — per-case (inline in result JSON)

Added fields on each `test_results[]` entry:
- `system_prompt` (string) — exact system prompt as sent to the model
- `user_prompt` (string) — exact user-turn content with RAG context already interpolated (for hybrid/rag-only modes)
- `prompt_tokens` (int) — non-zero
- `completion_tokens` (int) — non-zero
- `total_tokens` (int) — non-zero
- `latency_ms` (int) — non-zero, end-to-end inference latency

Plumbing: `GraphState` → `RagResponse` → `EvaluationResult` → DTO propagation of `llm_context`, `system_prompt`, token counts, `latency_ms` wired end-to-end.

### Captured payload — retrieved contexts (sidecar file)

- Lives in `{run_id}-contexts.json` alongside the result JSON
- Shape: `{ "test_id": [ { text, citation_id, section, score, ...metadata }, ... ] }` keyed by test id
- Each retrieved context entry contains **full chunk text plus all metadata** (citation_id, section, clause reference, rerank score, etc.)
- Only populated for `hybrid` and `rag-only` modes (llm-only has no retrieval)
- CLI `--verbose` reads sidecar and displays retrieved contexts inside per-test-case panel

### Schema versioning

- Bump JSON schema version from v5 → v6
- `metadata.run_id` is the marker field distinguishing v6 from v5
- Report tooling treats missing new fields as nullable — legacy v5 files remain readable
- No automatic migration of legacy flat-directory results into `{yyyy-MM}/` subdirs

### Claude's Discretion

- Exact token field naming convention (match Ollama API where possible: `prompt_eval_count`, `eval_count`, or normalised to OpenAI-style `prompt_tokens`/`completion_tokens`)
- Directory creation logic (lazy mkdir per month at write time)
- Glob pattern specifics for report tooling
- Whether to prune the sidecar file in llm-only mode or emit an empty shell
- How to handle existing pre-v6 result files during report glob (skip vs include with warning)

</decisions>

<specifics>
## Specific Ideas

- **Queries become auditable artifacts.** Currently `ccop-eval query ask` only prints to CLI — post-3.1, every query invocation writes a result JSON with `scope=query`, enabling full history of ad-hoc queries alongside eval runs.
- **Sidecar pattern for contexts** keeps per-run files small (~20 KB) while preserving full retrieval debuggability. Cheap to diff result JSONs across runs without pulling in multi-megabyte chunk text.
- **Nested monthly directory** will self-archive naturally as runs accumulate — no explicit cleanup logic needed for months.

</specifics>
