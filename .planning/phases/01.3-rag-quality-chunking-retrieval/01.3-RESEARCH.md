## Summary

Phase 1.3 fixes retrieval precision by replacing the broken PyMuPDF4LLM + MarkdownHeaderTextSplitter pipeline with Docling parser and clause-aware chunking, removing the incompatible RRF threshold, and adding cross-encoder reranking. The research focused on integration patterns for these components within the existing LangGraph architecture.

The existing broad research (artifacts/research/2026-03-02-rag-chunking-retrieval-strategies-technical.md) already identified the recommended stack (Docling, clause-aware regex chunking, ms-marco-MiniLM-L12-v2 cross-encoder). This research focuses on the "how" not the "what": integration points, API patterns, configuration requirements, and evaluation frameworks needed for planning.

**Key findings:**
- Docling provides both `DocumentConverter` (parsing) and `HybridChunker` (optional) APIs — we'll use converter, bypass built-in chunker for custom clause-aware logic
- Cross-encoder integration is a simple LangGraph node addition between retrieval and grading (sentence-transformers already installed)
- RAGAs metrics (context_precision, context_recall) require ground truth annotations — 94% of 118 test cases already have `clause_reference` field
- RRF threshold removal is configuration-only change (no code modification needed beyond grading node refactor)

**Primary recommendation:** Use Docling's classic pipeline (faster, deterministic) for parsing, implement custom clause-aware chunker to preserve regulatory structure, add cross-encoder as new LangGraph node, configure funnel shape (retrieve 20 → rerank → top 3), measure with RAGAs on existing test suite.

### Pattern 1: Docling Parser Integration
**What:** Replace PyMuPDF4LLM with Docling DocumentConverter to extract hierarchical structure from PDFs.

**When to use:** All 8 CCoP documents — same parser for all document types.

**Example:**
```python
# Source: https://docling-project.github.io/docling/concepts/chunking/
from docling.document_converter import DocumentConverter

def parse_ccop_pdf_with_docling(pdf_path: str, document_name: str) -> str:
    """
    Parse CCoP PDF using Docling with structure preservation.

    Returns markdown text with hierarchical structure intact.
    """
    converter = DocumentConverter()

    # Convert PDF to DoclingDocument
    result = converter.convert(pdf_path)
    doc = result.document

    # Export to markdown (preserves heading hierarchy)
    markdown_text = doc.export_to_markdown()

    return markdown_text
```

**Integration notes:**
- Docling auto-detects PDF structure — no manual configuration needed
- `export_to_markdown()` preserves heading levels and numbered clauses
- Use "classic" pipeline (default) not "VLM" (GPU-only, experimental)
- Docling runs on CPU — no GPU requirement for Phase 1.3

### Pattern 2: Clause-Aware Chunking
**What:** Split markdown on numbered clause boundaries using regex patterns that match CCoP structure (e.g., "5.2.1 The CIIO shall...").

**When to use:** After Docling parsing, before embedding generation.

**Example:**
```python
import re
from typing import List
from rag.ingestion.models import CcopChunk, ChunkMetadata

# Regex patterns for clause boundaries
CLAUSE_PATTERN = re.compile(
    r'^(\d+(?:\.\d+)*)\s+(.+?)$',  # Matches "5.2.1 Heading text"
    re.MULTILINE
)

def chunk_by_clauses(markdown_text: str, document_name: str) -> List[CcopChunk]:
    """
    Split markdown on numbered clause boundaries.

    Each chunk = one regulatory requirement (leaf-level clause).
    """
    chunks = []

    # Split on clause boundaries
    sections = CLAUSE_PATTERN.split(markdown_text)

    for i in range(1, len(sections), 3):
        clause_number = sections[i]
        clause_heading = sections[i+1]
        clause_content = sections[i+2] if i+2 < len(sections) else ""

        # Build chunk text (heading + content)
        chunk_text = f"{clause_number} {clause_heading}\n\n{clause_content}".strip()

        # Skip tiny chunks (cross-references, under ~30 tokens)
        if len(chunk_text.split()) < 30:
            continue  # Merge with parent in production implementation

        # Build metadata
        metadata = ChunkMetadata(
            document_source=document_name,
            section=extract_section(clause_number),  # "5.2" from "5.2.1"
            clause=clause_number,
            citation_id=f"{document_name}::{clause_number}",
            page=None,  # Docling provides page info if needed
        )

        chunks.append(CcopChunk(
            id=f"{document_name}::{clause_number}",  # No UUID — use clause ID
            text=chunk_text,
            metadata=metadata,
        ))

    return chunks
```

**Integration notes:**
- Chunk IDs use `{source_file}::{clause_id}` format — eliminates UUID collisions
- Parent hierarchy (chapter, section) stored in metadata only (not prepended to text per CONTEXT.md)
- Tables: detect markdown tables and keep entire table as one chunk
- Boilerplate exclusion: use Docling's document element types (page_header, page_footer) to filter

### Pattern 3: Cross-Encoder Reranking Node
**What:** Add LangGraph node that re-scores top-k candidates with cross-encoder before passing to LLM.

**When to use:** After hybrid retrieval (dense + sparse RRF), before grading node.

**Example:**
```python
# Source: https://huggingface.co/cross-encoder/ms-marco-MiniLM-L12-v2
from sentence_transformers import CrossEncoder
from rag.retrieval.state.graph_state import GraphState

# Lazy load cross-encoder (thread-safe singleton)
_cross_encoder = None

def get_cross_encoder():
    global _cross_encoder
    if _cross_encoder is None:
        _cross_encoder = CrossEncoder('cross-encoder/ms-marco-MiniLM-L12-v2')
    return _cross_encoder

def rerank_documents(state: GraphState) -> GraphState:
    """
    Re-score retrieved documents with cross-encoder.

    Takes top-k from retrieval (e.g., 20), re-scores with cross-encoder,
    returns top-N (e.g., 3) to downstream nodes.
    """
    query = state.get("rewritten_query", state.get("query", ""))
    documents = state.get("documents", [])
    top_n = 3  # Configurable via settings

    if not documents:
        state["reranker_scores"] = []
        return state

    # Prepare (query, passage) pairs
    pairs = [(query, doc.page_content) for doc in documents]

    # Score with cross-encoder
    model = get_cross_encoder()
    scores = model.predict(pairs)

    # Attach scores to documents
    for doc, score in zip(documents, scores):
        doc.metadata["reranker_score"] = float(score)

    # Sort by reranker score descending
    ranked_docs = sorted(
        zip(documents, scores),
        key=lambda x: x[1],
        reverse=True
    )

    # Keep top-N
    top_docs = [doc for doc, _ in ranked_docs[:top_n]]
    all_scores = [float(score) for score in scores]

    state["documents"] = top_docs
    state["reranker_scores"] = all_scores

    return state
```

**Integration notes:**
- Add node to LangGraph: `workflow.add_node("reranking", rerank_documents)`
- Insert edge: `retrieval → reranking → grade_documents`
- Latency: ~200ms for 20 candidates on CPU (acceptable for compliance queries)
- Funnel shape configurable: retrieve 20 → rerank → top 3 (via settings)

### Pattern 4: RAGAs Evaluation Integration
**What:** Measure retrieval quality using RAGAs context_precision and context_recall metrics on test suite.

**When to use:** After re-ingestion and pipeline changes, run on all 118 test cases.

**Example:**
```python
# Source: https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_precision/
from ragas import evaluate
from ragas.metrics import context_precision, context_recall
from datasets import Dataset

def evaluate_retrieval_quality(test_cases: List[dict], rag_pipeline):
    """
    Evaluate RAG pipeline on test suite using RAGAs metrics.

    Args:
        test_cases: List of test case dicts with 'question', 'clause_reference'
        rag_pipeline: RAG query function

    Returns:
        Dict with context_precision and context_recall scores
    """
    # Build RAGAs dataset
    data = {
        "question": [],
        "contexts": [],      # Retrieved chunks
        "ground_truth": [],  # Expected clause references
    }

    for case in test_cases:
        # Run RAG retrieval
        result = rag_pipeline(case["question"], mode="rag-only")

        # Extract retrieved contexts
        contexts = [doc.page_content for doc in result.get("filtered_documents", [])]

        data["question"].append(case["question"])
        data["contexts"].append(contexts)
        data["ground_truth"].append(case.get("clause_reference", ""))

    dataset = Dataset.from_dict(data)

    # Evaluate with RAGAs
    results = evaluate(
        dataset,
        metrics=[context_precision, context_recall],
    )

    return results
```

**Integration notes:**
- 118 test cases in ground-truth/phase-2/test-suite/ (JSONL format)
- 94% have `clause_reference` field — use as ground truth for retrieval metrics
- Group results by benchmark type: retrieval-focused (B2, B3, B5, B6, B12) vs reasoning-focused (B7-B20)
- Auto-generate experiment report: chunk stats, metrics per group, reranker score distribution

### Anti-Patterns to Avoid
- **Prepending parent hierarchy to chunk text:** Increases token count, dilutes embedding focus. Store hierarchy in metadata only (per CONTEXT.md decision).
- **Using Docling HybridChunker directly:** Designed for general documents, doesn't understand regulatory numbering (5.2.1 format). Custom clause-aware logic required.
- **Applying RRF threshold to reranker scores:** RRF scores and cross-encoder scores have different ranges. Use top-N selection, not threshold-based filtering.
- **LLM grading after cross-encoder:** Cross-encoder already provides query-document relevance. Grading node becomes measurement-only (logs scores, no filtering).

## Don't Hand-Roll

Problems that look simple but have existing solutions:

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| PDF hierarchical structure extraction | Regex on raw PDF text | Docling DocumentConverter | Handles tables, multi-column layouts, heading detection, page boundaries — edge cases are complex |
| Context precision/recall metrics | Custom LLM prompts for relevance | RAGAs framework | Standardized metrics, LLM-as-judge implementation, cross-validation with research benchmarks |
| Cross-encoder model loading/inference | Manual PyTorch model download | sentence-transformers CrossEncoder API | Auto-downloads, handles tokenization, thread-safe caching, optimized inference |
| Chunk ID generation | UUID-based hashing | Deterministic clause-based IDs | UUID collisions observed in baseline (87→66 chunks), clause IDs are human-readable and debuggable |

**Key insight:** PDF parsing and chunking are mature domains with battle-tested libraries (Docling is IBM Research). Hand-rolling regex-based PDF extraction will miss tables, footers, multi-column layouts. Evaluation metrics (RAGAs) benefit from standardization — comparable across experiments and with research literature.

## Common Pitfalls

### Pitfall 1: Docling VLM Pipeline Instead of Classic
**What goes wrong:** VLM pipeline requires GPU and is experimental (slower, higher resource usage).

**Why it happens:** Docling documentation shows VLM examples prominently, appears more "advanced".

**How to avoid:** Use default DocumentConverter() without arguments — auto-selects classic pipeline (CPU-compatible, production-ready).

**Warning signs:** Docling throws GPU requirement errors, parsing takes >5 seconds per page.

### Pitfall 2: RRF Score Range Mismatch
**What goes wrong:** Applying cosine similarity threshold (0.6) to RRF scores (~0.001-0.033) filters out all results.

**Why it happens:** RRF scores are rank-based (1/k formula), not similarity-based (0-1 range). Settings threshold was designed for cosine but applied to both retrieval modes.

**How to avoid:** Remove threshold entirely for RRF path. Use top-N selection (retrieve 20, rerank, return top 3) instead of score-based filtering.

**Warning signs:** No documents pass grading step, all RRF scores below 0.1, retrieval always triggers fallback.

### Pitfall 3: Chunk ID Collisions with UUID
**What goes wrong:** `uuid5(NAMESPACE, "docname-0")` generates identical IDs when different documents have chunks at same index. 87 chunks reduced to 66 after deduplication.

**Why it happens:** UUID namespace+seed doesn't include unique document identifier — only chunk index.

**How to avoid:** Use deterministic IDs based on source file and clause number: `{source_file}::{clause_id}` (e.g., "CCoP-2.0::5.2.1").

**Warning signs:** Chunk count lower than expected, multiple documents with same chunk index, Qdrant logs "duplicate point ID" warnings.

### Pitfall 4: Including Table of Contents in Index
**What goes wrong:** ToC entries rank higher than actual content because they contain all document keywords densely packed.

**Why it happens:** ToC is semantically similar to queries (contains all section names) but has no regulatory content.

**How to avoid:** Use Docling's document element types to filter out `page_header`, `page_footer`, `toc` elements before chunking.

**Warning signs:** Retrieved chunks are ToC entries, citations resolve to "Table of Contents" instead of clause numbers.

### Pitfall 5: RAGAs Metrics Without Ground Truth
**What goes wrong:** RAGAs context_recall requires reference answers — can't measure what "should" be retrieved without ground truth.

**Why it happens:** RAGAs documentation shows unsupervised metrics (faithfulness, answer_relevancy) first.

**How to avoid:** Verify test cases have `clause_reference` or `expected_response` fields before running context_precision/context_recall. Use LLM-as-judge for unlabeled queries.

**Warning signs:** RAGAs throws "missing ground_truth field" error, context_recall always 0.0 or N/A.

### Docling PDF Parsing with Structure Preservation
```python
# Source: https://docling-project.github.io/docling/concepts/chunking/
from docling.document_converter import DocumentConverter
from pathlib import Path

def parse_ccop_documents(ccop_dir: str) -> dict[str, str]:
    """
    Parse all CCoP PDFs with Docling.

    Returns dict mapping document name to markdown text.
    """
    converter = DocumentConverter()
    parsed_docs = {}

    for pdf_path in Path(ccop_dir).rglob("*.pdf"):
        # Convert PDF to DoclingDocument
        result = converter.convert(str(pdf_path))
        doc = result.document

        # Export to markdown (preserves hierarchy)
        markdown = doc.export_to_markdown()

        parsed_docs[pdf_path.stem] = markdown

    return parsed_docs
```

### LangGraph Pipeline with Reranking Node
```python
# Source: Existing graph.py pattern
from langgraph.graph import StateGraph, END
from rag.retrieval.nodes.retrieval import retrieve_documents
from rag.retrieval.nodes.reranking import rerank_documents
from rag.retrieval.nodes.grading import grade_documents
from rag.retrieval.state.graph_state import GraphState

def build_rag_graph_with_reranking(settings):
    workflow = StateGraph(GraphState)

    # Nodes
    workflow.add_node("retrieval", retrieve_documents)
    workflow.add_node("reranking", rerank_documents)  # NEW
    workflow.add_node("grade_documents", grade_documents)

    # Edges
    workflow.set_entry_point("retrieval")
    workflow.add_edge("retrieval", "reranking")       # NEW
    workflow.add_edge("reranking", "grade_documents") # MODIFIED
    workflow.add_edge("grade_documents", END)

    return workflow.compile()
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| PyMuPDF4LLM flat markdown | Docling hierarchical parsing | 2024-2025 | Structure-aware parsing became standard for regulatory/legal docs |

**Deprecated/outdated:**
- **PyMuPDF4LLM for structured documents:** Replaced by Docling (IBM Research, 97.9% table accuracy, hierarchy preservation). PyMuPDF4LLM is fine for simple text extraction but loses structure.
- **Score thresholds on RRF:** RRF scores are rank-based (1/k formula), not similarity-based. Use top-N selection instead.
- **UUID-based chunk IDs:** Deterministic clause-based IDs (`{source}::{clause}`) prevent collisions and enable human debugging.

## Open Questions

Things that couldn't be fully resolved:

1. **Exact clause boundary regex patterns for all 8 documents**
   - What we know: CCoP main document uses "5.2.1 Heading" format consistently
   - What's unclear: Supplementary documents (Auditing Guidelines, Threat Modelling) may use different numbering schemes
   - Recommendation: Test regex patterns against all 8 PDFs during implementation, add special cases if needed

2. **Optimal minimum token threshold for tiny clause merging**
   - What we know: CONTEXT.md suggests ~30 tokens as threshold for merging with parent
   - What's unclear: Whether 30 tokens is too aggressive (merges real clauses) or too lenient (keeps cross-references)
   - Recommendation: Start with 30 tokens, measure chunk size distribution after ingestion, adjust if needed

3. **Docling classic vs VLM pipeline performance**
   - What we know: Classic is CPU-compatible and faster, VLM requires GPU
   - What's unclear: Whether VLM provides measurably better hierarchy extraction for CCoP documents
   - Recommendation: Start with classic (faster, production-ready), evaluate VLM if classic misses critical structure

4. **RAGAs LLM-as-judge model choice**
   - What we know: RAGAs uses LLM to judge relevance for context_precision/context_recall
   - What's unclear: Whether to use local Primus-Reasoning (slow) or OpenAI API (cost) for evaluation
   - Recommendation: Use OpenAI gpt-4o-mini for evaluation (cheap, fast) unless local-only is hard requirement
