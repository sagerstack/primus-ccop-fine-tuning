# Phase 12 — Agentic `graphont` Retrieval-Quality Loop

**Date:** 2026-07-13  
**Mode strategy:** add new mode `graphont-agentic`; preserve `graphont` unchanged per ADR-008  
**Primary goal:** improve retrieval quality first, so citation accuracy and D6 rise **because the right clauses are retrieved and grounded**, not because citations are cleaned up post-generation.

## 1. Decision record for Phase 12

### Locked decisions
- **Do not ship Slice 1.5 in the benchmark path.**
  - Reason: stripping fabricated citations post-generation would alter the judged artifact without improving retrieval.
  - Evaluation integrity matters more than cosmetic D6 gains.
- **Phase 12 focuses on Slice 3 first.**
  - Retrieval-first improvement aligns with the stated objective.
- **No extra LLM in Slice 3 v1.**
  - No separate controller/judge/planner call to assess retrieval quality.
  - The first version uses a deterministic, stateful retrieval loop.
- **Ground truth may be used offline only.**
  - Use GT to calibrate and evaluate retrieval weakness detection.
  - Never use GT in the runtime retrieval loop.
- **Backward compatibility is mandatory.**
  - `graphont` remains the control.
  - New behavior lives behind `graphont-agentic` only.

### Deferred decisions
- Whether a later Slice 3 v2 should use the same local Primus model for query reformulation/path planning.
- Whether RoG-style path planning is needed after parameter-only and graph-expansion retries are tested.
- Whether `requery_count` should remain `<=1` or expand to `<=2` after calibration.

---

## 2. Research basis for the chosen approach

### Primary basis
- **CRAG** (Corrective RAG)
  - Use a retrieval-quality assessment signal.
  - If retrieval is weak, trigger a bounded corrective retrieval action before generation.

### Graph-specific retrieval basis
- **HippoRAG**
  - Use graph-seeded expansion / Personalized PageRank-like neighborhood expansion as a cheap recall recovery step.
  - This is the preferred first graph-aware correction because it does not require an extra LLM call.

### Supporting pattern
- **Adaptive-RAG**
  - Use lightweight routing logic so only weak cases pay the retry cost.

### Explicitly deferred
- **RoG**
  - Valuable if multi-hop graph path planning is needed.
  - Deferred until Phase 12 proves deterministic retry and graph expansion are insufficient.
- **ReAct/tool agent**
  - Out of scope for evaluation mode due to determinism and attribution concerns.

---

## 3. What Phase 12 is building

Phase 12 adds a bounded agentic retrieval loop to `graphont`:

```text
query_analysis
  -> route_by_mode("graphont-agentic")
  -> omd_retrieve
  -> assess_retrieval_quality
      -> if strong: omd_pack -> generate -> END
      -> if weak and under cap: plan_requery -> omd_retrieve -> assess_retrieval_quality
      -> if weak and at cap: omd_pack -> generate -> END
```

### Why this still counts as agentic
The loop is **stateful and conditional**:
- it inspects retrieval outcomes,
- decides whether retrieval is good enough,
- chooses a corrective action,
- retries retrieval before generation.

For v1, the decision policy is deterministic rather than LLM-based.

---

## 4. Core Phase 12 question

> Can we reliably detect weak `graphont` retrieval from internal retrieval signals, and can one bounded corrective retrieval step improve clause availability enough to improve downstream citation accuracy and D6?

This phase answers that question in two parts:
1. build a **weak-retrieval detector**;
2. apply **one corrective retrieval action at a time** and measure impact.

---

## 5. Weak retrieval definition

Weak retrieval must be defined **offline first** using real `graphont` runs.

### Retrieval outcome labels
Each calibration case should be labeled as one of:
- **strong**
  - retrieved context contains the clause(s) needed for a correct grounded answer;
- **weak-recall**
  - needed clause(s) are missing from retrieved context;
- **weak-focus**
  - relevant region is present, but ranking/context is dominated by distracting or generic material;
- **empty**
  - retrieval returned nothing useful.

### Important note
These are **evaluation labels**, not runtime outputs. Runtime uses heuristics derived from them.

---

## 6. Use of ground truth

### Allowed use
Use GT **offline** to:
- label retrieval as strong/weak-recall/weak-focus/empty;
- compute coarse clause-hit@k / recall@k;
- compare before-vs-after retry retrieval quality;
- estimate whether retry surfaces expected clause references more often.

### Prohibited use
Do **not** use GT at runtime to:
- decide whether retrieval is weak;
- select the retry action;
- inject known-good clauses.

### GT framing
GT clause references are a **silver oracle**, not a perfect oracle:
- useful for measuring retrieval improvements;
- not exhaustive enough to define the only acceptable support.

---

## 7. Signals to evaluate as weak-retrieval predictors

Phase 12 starts by inventorying which signals already exist in `graphont` retrieval output and state.

### Candidate signals
- `retrieval_succeeded`
- `ce_confidence`
- reranker top-1 score
- reranker top-k mean
- top-1 vs top-2 / top-3 margin
- per-channel contribution (`graph`, `bm25`, `dense`)
- channel disagreement / instability
- candidate count before rerank
- candidate count after rerank
- concept/entity coverage from query analysis
- clause specificity / genericity of returned contexts
- whether final generated citations were present in retrieved context

### First deliverable
Produce a signal inventory table documenting:
- signal name,
- source file,
- availability today,
- whether already persisted to `GraphState`,
- whether deterministic and cheap enough for runtime gating.

## 8. Phase 12 implementation slices

# 8.1 Slice A — retrieval weakness calibration framework

### Objective
Create the offline framework used to decide what “weak retrieval” means in this codebase.

### Steps
1. Select a calibration set.
   - Start with 20–40 cases.
   - Include known `graphont` misses and known good cases.
   - Ensure coverage across multiple benchmark families.
2. Run baseline `graphont` retrieval traces.
3. Capture per-case retrieval artifacts.
   - retrieved candidates;
   - scores;
   - channel provenance;
   - `ce_confidence`;
   - final assembled context;
   - final generated citations.
4. Label each case offline as `strong`, `weak-recall`, `weak-focus`, or `empty`.
5. Compare labels against GT clause references and judged outputs.
6. Identify which signals best separate strong vs weak.
7. Propose a v1 deterministic weakness detector.

### Outputs
- calibration set definition;
- per-case labeled dataset;
- signal analysis summary;
- recommended v1 weakness rule.

### Success criteria
- We can explain why each case is strong or weak.
- We have evidence for which runtime signals are useful.
- We avoid guessing thresholds blindly.

---

# 8.2 Slice B — split `omd_context_assembly` into retrieval and packing

### Objective
Refactor `graphont` internals so retrieval can be retried without duplicating packing/generation logic.

### Required code change
Replace the monolithic node with two conceptual stages:
- `omd_retrieve`
- `omd_pack`

### Responsibilities
#### `omd_retrieve`
- invoke the OMD retrieval provider;
- collect raw retrieval outputs;
- persist retrieval metadata to `GraphState`.

#### `omd_pack`
- transform chosen candidates into generation-ready context;
- preserve current `graphont` packing semantics unless mode is `graphont-agentic`.

### Success criteria
- `graphont` remains behavior-identical.
- `graphont-agentic` can re-enter retrieval without awkward duplication.

---

# 8.3 Slice C — deterministic weak-retrieval detector

### Objective
Build the runtime decision node that classifies retrieval as strong or weak.

### v1 rule shape
Start with a simple deterministic policy, e.g.:

```text
weak if:
  not retrieval_succeeded
  OR ce_confidence < tau_conf
  OR top1_rerank_score < tau_top1
  OR top1_top2_margin < tau_margin in low-confidence cases
  OR concept_coverage < tau_coverage
```

Final thresholds must come from Slice A calibration.

### Runtime outputs
The node should write fields such as:
- `retrieval_grade`: `strong | weak-recall | weak-focus | empty`
- `retrieval_grade_reasons`: list of triggered conditions
- `should_requery`: boolean

### Important constraint
The detector should be **interpretable**.
Every retry decision must be explainable from persisted state.

---

# 8.4 Slice D — corrective action 1: parameter-only retry

### Objective
Test the cheapest corrective action first.

### When used
Use when retrieval is weak but the case does not justify graph expansion yet.

### Allowed actions
- widen retrieval `k`;
- increase recall depth;
- adjust channel weights;
- relax restrictive thresholds/filters if present;
- rerun reranking on the expanded candidate pool.

### Why first
This isolates whether the problem is simply first-pass narrowness.

### Runtime state to persist
- chosen retry action;
- before/after parameters;
- before/after candidate counts;
- before/after confidence/score summaries.

### Evaluation question
Does a single wider retry increase expected-clause presence or downstream citation grounding?

---

# 8.5 Slice E — corrective action 2: graph expansion retry

### Objective
If parameter widening is insufficient, test graph-aware recall recovery.

### Basis
HippoRAG-style graph expansion.

### v1 implementation guidance
- derive seed concepts from query analysis and/or top retrieved concepts;
- expand over graph relations already available in the OMD graph (e.g. `:REL`, `:INVOKES`);
- gather neighboring candidate clauses/concepts;
- merge with first-pass candidates;
- rerank merged candidates;
- repack and generate.

### Constraint
Do not introduce an extra LLM in v1.
This is graph-based, deterministic expansion only.

### Evaluation question
When the first pass misses a needed clause, does graph expansion recover it more often than widening alone?

---

# 8.6 Slice F — route policy between corrective actions

### Objective
Choose one corrective action based on weakness type.

### v1 policy
- `empty` -> `retry_wider`
- `weak-recall` -> `retry_graph_expand`
- `weak-focus` -> `retry_wider`
- all others -> `accept_retrieval`

If calibration suggests a different mapping, update this table.

### Cap
- v1: `requery_count <= 1`
- any increase requires fresh evaluation evidence

### Runtime action set
- `accept_retrieval`
- `retry_wider`
- `retry_graph_expand`
- `stop_after_cap`

---

# 8.7 Slice G — evaluation harness for retrieval improvement

### Objective
Measure whether retrieval actually improved before claiming citation gains.

### Metrics
#### Runtime / instrumentation
- requery rate
- empty retrieval rate
- before/after `ce_confidence`
- before/after top-1/top-k scores
- action distribution
- latency delta

#### Offline retrieval metrics
- coarse GT clause hit@k
- coarse GT recall@pool
- percent of final citations present in retrieved context
- percent of cases where retry introduced a final cited clause

#### End-to-end metrics
- D6
- citation grounding metrics already used by the evaluator
- benchmark-family deltas on the calibration set and then broader runs

### Critical causal metric
Track:
- **Did retry surface a clause that later appeared in the final citation set?**

This is the cleanest indicator that the retrieval loop mattered.

### Unit tests
- weakness detector classification from fixed retrieval fixtures;
- retry policy action selection;

- calibration-set retrieval metrics improve;
- some fraction of final citations are newly surfaced by retry;

## 12. Acceptance criteria for Phase 12

Phase 12 is successful if all of the following hold:
- `graphont-agentic` exists as a separate additive mode.
- `graphont` behavior remains unchanged.
- A deterministic weak-retrieval detector is defined from observed data, not intuition.
- At least one bounded corrective retrieval action is implemented and measured.
- We can show whether retry improved retrieval using offline GT-based diagnostics.
- We can trace when retry introduced a clause later used in the final answer.
- Any D6 improvement can be credibly attributed to better retrieval, not post-hoc citation cleanup.

### Primary vs secondary success metric (scope clarification)
- **Primary metric = retrieval recall against GT.** Phase 12 is scoped to retrieval quality: success is measured by whether the retrieved context contains the GT-relevant clause(s) — i.e. before/after `clause-hit@k` / `recall@pool` improves, and specifically whether a retry surfaces a previously-missing GT clause into the pool.
- **D6 is a secondary / observational metric, not the primary bar.** D6 is downstream and confounded by the model's citation/attribution behavior, which Phase 12 deliberately does not touch (citation-cleanup / Slice 1.5 excluded). Whether the model *chooses to cite* a correctly-retrieved clause is out of scope for this phase.
- **Therefore: improved GT clause recall with flat D6 is still a Phase 12 success** — the retrieval objective was met. Do not gate Phase 12 on D6 movement; report D6 as an observational downstream signal only. (A separate later phase may address the "model ignored correctly-retrieved context" failure mode.)

## 13. Risks and controls

### Risk: weak detector is noisy
- **Control:** start with interpretable rules and a labeled calibration set.

### Risk: GT clause refs are incomplete
- **Control:** use GT as a silver retrieval oracle; keep D6 as the final external metric.

### Risk: refactor breaks `graphont`
- **Control:** parity tests before activating the new mode.

### Risk: retries add cost without value
- **Control:** add actions one at a time and compare against baseline.

### Risk: graph expansion adds irrelevant noise
- **Control:** test widened retry first, then graph expansion, and keep reranking in the loop.

## 15. Summary

Phase 12 deliberately narrows scope:
- **no citation-cleanup slice** in the eval path,
- **no extra LLM** in Slice 3 v1,
- **yes** to offline GT-based calibration,
- **yes** to a deterministic retrieval-quality gate,
- **yes** to one bounded retry action at a time.

The implementation order is:
1. define weak retrieval from real cases,
2. expose and analyze retrieval signals,
3. split retrieval from packing,
4. add deterministic weakness detection,
5. test parameter-only retry,
6. test graph expansion retry,
7. evaluate whether retrieval improvements causally improve citation quality.
