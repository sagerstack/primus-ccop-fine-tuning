# Phase 12 (rev 02) — Agentic `graphont` Retrieval-Quality Loop

**Date:** 2026-07-13
**Supersedes:** `12-01-PLAN.md` (original design)
**Revision basis:** peer-reviewed research critique — `research/20260713-agentic-rag-critique/FINAL-agentic-rag-critique.md`
**Mode strategy:** add new mode `graphont-agentic`; preserve `graphont` unchanged per ADR-008
**Primary goal:** improve **retrieval quality** first — success is measured by whether the retrieved context contains the GT-relevant clause(s), so that citation accuracy and D6 *can* rise because the right clauses are retrieved and grounded.

---

## 0. What changed from 12-01 (changelog)

The research critique **affirmed the strategy and architecture** and produced a strengthening pass, not a redirection. Concentrated changes:

- **Rework — weakness detector (§8.3):** replace the wide-OR soft-threshold rule with a **two-tier gate** (hard-failure OR sentinels + locally-calibrated soft-evidence consensus/AND over rank-normalized features). Reranker/retrieval scores certify *topicality, not answer support*; a wide OR of several soft, high-frequency triggers over-fires.
- **Rework — action routing (§8.6):** derive the route table from an **offline action-oracle**, not intuition. `weak-focus → retry_wider` in particular is a high-risk guess.
- **Fix — signal inventory (§7):** **remove "final citations present in retrieved context" from the runtime detector** — it is only knowable post-generation. Retain it as an offline diagnostic only.
- **Revise — graph expansion (§8.5):** make it **typed, hub-safe, provenance-first**. The `CII` hub (≈⅓ of the graph) is a Static-Graph-Fallacy / hub-drift hazard.
- **Revise — calibration & evaluation (§8.1, §8.7):** 20–40 cases cannot both tune and validate. Require **disjoint calibration / held-out / test splits**, pooled expert adjudication, stratification, bootstrap CIs, a full-chain retrieval metric, and two counterfactuals (retry-ablation + offline action-oracle).
- **Revise — runtime taxonomy (§5):** runtime emits coarse `strong / low_confidence / empty`; the finer `weak-recall / weak-focus` labels stay **offline** until held-out evidence proves the distinction is learnable.
- **Reframe — research basis (§2):** CRAG / HippoRAG / Adaptive-RAG are adopted at the **pattern level**, not mechanistically; document this to avoid over-claiming validation.
- **Clarify — success metric (§12):** **retrieval recall vs GT is primary; D6 is secondary/observational.** Improved clause recall with flat D6 is still a Phase 12 success.

**Unchanged (affirmed by the critique):** all §1 locked decisions, the additive/backward-compatible mode, GT-offline-only, the loop architecture, the slice ordering, and the deferral of RoG / ReAct / query-reformulation.

## 2. Research basis (adopted at the pattern level)

Phase 12 borrows *concepts*, not *mechanisms*. Document this explicitly so results are not over-interpreted.

- **CRAG (Corrective RAG)** — pattern: post-retrieval quality gate → bounded corrective action. *Omitted:* CRAG's trained T5 evaluator, refinement, external web search. Phase 12 substitutes interpretable deterministic heuristics for the trained gate.
- **HippoRAG / HippoRAG 2** — pattern: graph-seeded neighborhood expansion for recall recovery. *Omitted:* Personalized PageRank, passage-node integration, online LLM recognition memory. The closest no-extra-LLM analogue is typed seeds + degree-normalized PPR/bridge scoring + verbatim source-text map-back.
- **Adaptive-RAG** — pattern: route weak vs strong cases to different retrieval effort. *Omitted:* trained query-complexity classifier and pre-retrieval routing (Phase 12 adapts *after* first retrieval).
- **Explicitly deferred:** RoG (path planning) — only if the offline oracle shows the graph contains the needed path but deterministic bridge/PPR repeatedly misses it. ReAct/tool agent — out of scope for evaluation determinism.

> Naming: keep the external mode name `graphont-agentic`, but describe it in prose as a **bounded corrective / "agentic-lite" GraphRAG controller** — it has state, observation, conditional routing, and termination, but performs no autonomous semantic planning. A negative result disproves only *this fixed controller*, not agentic RAG in general.

## 3. What Phase 12 is building

A bounded agentic retrieval loop added to `graphont`:

```text
query_analysis
  -> route_by_mode("graphont-agentic")
  -> omd_retrieve
  -> assess_retrieval_quality          # two-tier deterministic gate
      -> if confident (strong): omd_pack -> generate -> END
      -> if low_confidence/empty and under cap:
             plan_requery              # action chosen from oracle-derived table
             -> omd_retrieve -> assess_retrieval_quality
      -> if low_confidence and at cap: omd_pack -> generate -> END
                                       # OR explicit insufficient-evidence outcome (policy)
```

Still agentic in the workflow sense (stateful, observes outcomes, conditional routing, terminates); the decision policy is deterministic, not LLM-based, in v1.

## 4. Core Phase 12 question

> Can we reliably detect weak `graphont` retrieval from internal retrieval signals, and can one bounded corrective retrieval step improve **clause availability in the retrieved pool** (GT clause recall) enough to matter?

Answered in two parts: (1) build a **weak-retrieval detector** from observed data; (2) apply **one corrective retrieval action at a time** and measure the recall impact. Downstream citation/D6 change is observed but not the pass bar (see §12).

---

## 5. Weak-retrieval definition (offline labels vs runtime outputs)

### Offline evaluation labels (for calibration only)
Each calibration case is labeled one of:
- **strong** — retrieved context contains the clause(s) needed for a correct grounded answer;
- **weak-recall** — needed clause(s) missing from retrieved context;
- **weak-focus** — relevant region present but dominated by distracting/generic material;
- **empty** — retrieval returned nothing useful.

### Runtime outputs (coarser on purpose)
Runtime emits **`strong` / `low_confidence` / `empty`** plus persisted trigger reasons. Do **not** emit `weak-recall` / `weak-focus` at runtime unless held-out evidence shows the system can actually distinguish them from pre-generation signals (they are semantic and not knowable from scores alone). Promote to the finer taxonomy only when calibration justifies it.

---

## 6. Use of ground truth (unchanged discipline, tighter evaluation)

### Allowed (offline)
Label retrieval strong/weak; compute coarse `clause-hit@k` / `recall@pool`; compare before-vs-after retry; estimate whether retry surfaces expected clauses more often.

### Prohibited (runtime)
Never use GT at runtime to decide weakness, select the retry action, or inject known-good clauses.

### GT framing
GT clause references are an **incomplete silver oracle**, not a perfect one: useful for measuring retrieval improvement, not exhaustive enough to define the only acceptable support. Because labels are incomplete, pool + expert-adjudicate alternative support during evaluation (see §8.7).

---

## 7. Signals to evaluate as weak-retrieval predictors

### Runtime-available candidate signals (pre-generation only)
- `retrieval_succeeded` (hard sentinel)
- empty / near-empty candidate pool (hard sentinel)
- **rank-normalized** bi-encoder & cross-encoder score distributions (not raw values)
- top-1/top-k margin & entropy **conditioned on pool size**
- cross-channel agreement / disagreement (`graph`, `bm25`, `dense`)
- candidate count before / after rerank
- query concept / entity / **relation** coverage from query analysis
- source / section / clause-family / document **diversity**
- whether retrieved clauses form a **connected, query-aligned subgraph**; provenance-text availability
- exact/rare-term coverage (clause numbers, regulator names, deadlines, exceptions)

### Removed from runtime (fix)
- ~~whether final generated citations were present in retrieved context~~ — **post-generation only**. Retain strictly as an **offline diagnostic**; it must never gate a pre-generation decision.

### First deliverable
Signal inventory table: signal name, source file, availability today, whether persisted to `GraphState`, whether deterministic/cheap for runtime gating, and **causal availability (pre- vs post-generation)**.

## 8. Implementation slices

### 8.0 Slice A0 — signal & pool baseline (new, cheap, do first)
**Objective:** before building anything, export real `graphont` traces on the calibration set and confirm which candidate signals in §7 actually exist and are reliable, and measure the current `clause-hit@k` / `recall@pool` baseline. This grounds every threshold and prevents blind guessing.
**Output:** signal-availability table + baseline recall numbers.

### 8.1 Slice A — retrieval-weakness calibration framework (revised: split discipline)
**Objective:** define "weak retrieval" from real cases with an overfit-proof protocol.
**Steps:**
1. Select a stratified calibration set (start 20–40; enlarge if a held-out split leaves too few per stratum). Stratify by: active benchmark family, single- vs multi-clause need, known graph miss, corpus-boundary case, clause specificity. Include known misses and clean successes.
2. **Freeze the set before any tuning.** Partition into **disjoint development / validation / untouched-test** splits. Never report the development (tuning) set as an improvement.
3. Run baseline `graphont` retrieval traces (Slice A0 export).
4. Capture per-case artifacts: candidates, scores, channel provenance, `ce_confidence`, assembled context, final citations (offline only).
5. Label each case `strong` / `weak-recall` / `weak-focus` / `empty` with rationale.
6. Compare labels vs GT clause references and judged outputs; down-weight single-preprint numeric thresholds.
7. Identify which signals best separate strong vs weak on **development**, confirm on **validation**.
8. Propose a v1 deterministic weakness rule (feeds §8.3).
**Success criteria:** we can explain each case's label; we have held-out evidence for useful signals; thresholds are calibrated, not guessed.

### 8.2 Slice B — split `omd_context_assembly` into retrieval and packing (unchanged)
Replace the monolithic node with `omd_retrieve` (invoke OMD provider; collect raw outputs; persist retrieval metadata to `GraphState`) and `omd_pack` (transform chosen candidates into generation-ready context; preserve current `graphont` packing semantics unless mode is `graphont-agentic`).
**Success criteria:** `graphont` behavior-identical (golden-trace parity); `graphont-agentic` can re-enter retrieval cleanly.

### 8.3 Slice C — two-tier deterministic weak-retrieval detector (rework)
**Objective:** classify retrieval as confident vs low-confidence with an interpretable, low-false-positive gate.

**v1 rule shape:**
- **Tier 1 — hard-failure sentinels (OR):** `not retrieval_succeeded` OR `empty`/near-empty pool → immediate `empty`/`low_confidence`.
- **Tier 2 — soft evidence (calibrated consensus / AND, or the single best held-out rule):** over rank-normalized pre-generation features (dual-score distributions, pool-size-conditioned margin/entropy, cross-channel agreement, concept/entity/relation coverage, source/clause diversity, subgraph connectedness, provenance availability, rare-term coverage). A single noisy soft condition must **not** trigger a retry on its own.

Thresholds come from Slice A held-out calibration, tuned for the chosen false-positive / false-negative cost.

**Runtime outputs:** `retrieval_grade`: `strong | low_confidence | empty`; `retrieval_grade_reasons`: triggered conditions; `should_requery`: bool. Every retry decision must be explainable from persisted state.

### 8.4 Slice D — corrective action 1: parameter-only retry (unchanged intent)
Cheapest action first: widen `k` / recall depth, adjust channel weights, relax over-restrictive filters, rerun reranking on the expanded pool. Persist chosen action + before/after params, candidate counts, and score summaries. **Make "wide hybrid + rerank" a mandatory comparator before crediting graph expansion.**

### 8.5 Slice E — corrective action 2: typed, hub-safe graph expansion (revised)
**Basis:** HippoRAG-style recall recovery, hardened against `graphont`'s hub structure.
**v1 implementation (no new LLM):**
- Reuse Stage-1 selected concepts as anchors; expand only **rarity-passing** concepts (existing §16.2 rarity gate); score candidate edges by query-concept alignment before merge.
- Prefer **bridge nodes** connecting ≥2 query seeds; **penalize hubs** (degree-normalized PPR / bridge discovery as escalation, not first resort).
- Cap hops / paths-per-seed-pair / nodes / context-tokens.
- Merge with the original lexical/dense pool and **rerank jointly**; apply novelty/diversity to avoid near-duplicate filling.
- **Map every graph node/path back to verbatim clause text; generate from source text, not graph summaries.**
- Persist traversal provenance: seeds + origin, edge types, path scores, expanded/visited-but-uncited nodes, map-back clause IDs, before/after candidate & score deltas.
**Guards against:** hub-drift / Static-Graph-Fallacy (CII ≈⅓ of graph), graph incompleteness (cannot traverse a missing path), triple extraction/detail loss, provenance under-reporting.

### 8.6 Slice F — route policy derived from an offline action-oracle (rework)
**Objective:** choose one corrective action per weakness signature — empirically, not by intuition.
**Method:** for every detector-positive calibration case, run all allowed actions `{no-retry, wider+rerank, prune/diversify, typed graph-expand}` and measure conditional utility (recall gain, harmful-retry rate). Build the route table from observed conditional utility; freeze v1. The oracle **never** enters runtime.
**Illustrative mapping (to be confirmed by the oracle, not assumed):**
- no candidates / over-restrictive filtering → relax filters; widen sparse+dense
- channel disagreement / rare exact terms absent → reweight lexical / hybrid retry
- adequate pool but flat/noisy reranker scores → rerank wider pool; diversity/coverage selection
- multiple query entities retrieved but disconnected → typed bridge / bounded degree-normalized PPR
- seed/entity alignment failure → *deferred* reformulation (escalation)
**Cap:** v1 `requery_count <= 1`; evaluate 0/1/2 (§8.7) before any increase.
**Runtime action set:** `accept_retrieval`, `retry_wider`, `retry_graph_expand`, `stop_after_cap`, plus an explicit `insufficient_evidence` outcome (if retry stays low-confidence, do not present evidence as sufficient — abstain or fall back to unchanged baseline per policy).

### 8.7 Slice G — evaluation harness for retrieval improvement (expanded)
**Objective:** prove retrieval improved (recall-first) with an overfit-proof protocol.

Evaluate at four levels + two counterfactuals:

| Level | Metrics |
|---|---|
| **Detector** | precision/recall/F1, false-positive & harmful-retry rate, calibration, confusion by failure type, per-benchmark-family |
| **Retrieval (PRIMARY)** | `clause-hit@k`, `recall@pool`, MRR/nDCG, **full-chain retrieval** (all gold clauses present *together*), pooled clause coverage, source/section diversity, subgraph connectivity, provenance availability, before/after candidate deltas |
| **Trajectory / action** | requery rate, action distribution, success/harm per action, marginal utility, hop/path count, stop reason, visited-vs-cited evidence, 0/1/2-cap ablation |
| **End-to-end (SECONDARY / observational)** | D6, claim-level citation entailment & completeness, abstention, latency mean/p95, tokens, regression rate, bootstrap CIs |

**Counterfactuals:** (1) **retry-ablation** — regenerate with retry-only clauses removed, other context fixed; did the claimed gain disappear? (2) **offline action-oracle** — per weak case, run all allowed actions to estimate the ceiling and expose route-policy errors.

**Protocol guards:** disjoint dev/validation/test; pool baseline + every retry variant and have an expert label *all* valid supporting clauses (including alternatives absent from GT); report silver-GT *and* pooled-expert metrics; bootstrap CIs + per-family deltas; retain an untouched broader run for the final claim. **20–40 cases are for instrument discovery, not threshold selection plus a performance claim across 435 cases.**

## 11. Testing strategy
**Unit:** two-tier detector classification from fixtures; retry action selection; `requery_count` cap; graphont vs graphont-agentic route separation.
**Regression:** `graphont` output unchanged after refactor (byte/structure golden traces); existing live modes unaffected per ADR-008.
**Integration:** low-confidence triggers exactly one retry; retry updates state and proceeds to pack/generate; empty retrieval is inspected (not silent straight-through) in `graphont-agentic`.
**Evaluation:** calibration-set `recall@pool` / `clause-hit@k` improve on held-out; some fraction of retries surface a previously-missing GT clause; D6 observed (not gated).

## 12. Acceptance criteria

Phase 12 (rev 02) is successful if all hold:
- `graphont-agentic` exists as a separate additive mode; `graphont` behavior unchanged.
- **HARD GATE — `graphont` golden-trace parity (byte/structure identical: candidate order → packed context → generation prompt) is verified before `graphont-agentic` is activated; a parity failure BLOCKS the phase.** The shared corpus/index (`ccop_clauses_hybrid`) is not modified. `graphont` must remain runnable for future eval/comparison.
- A **two-tier deterministic** weak-retrieval detector is defined from observed, held-out data — not intuition.
- At least one bounded corrective retrieval action (with typed/hub-safe graph expansion available) is implemented and measured.
- Retrieval improvement is shown with an **overfit-proof** protocol (disjoint splits, pooled adjudication, bootstrap CIs, full-chain metric).
- We can trace when retry introduced a GT clause into the retrieved pool.

### Primary vs secondary success metric (scope clarification)
- **Primary = retrieval recall against GT.** Success is whether the retrieved context contains the GT-relevant clause(s): before/after `clause-hit@k` / `recall@pool`, and whether a retry surfaces a previously-missing GT clause into the pool.
- **D6 is secondary / observational.** It is downstream and confounded by the model's citation/attribution behavior, which Phase 12 deliberately does not touch (Slice 1.5 excluded). Whether the model *chooses to cite* a correctly-retrieved clause is out of scope.
- **Improved GT clause recall with flat D6 is still a Phase 12 success.** Do not gate the phase on D6 movement; report it as an observational downstream signal only.

## 13. Risks and controls
- **Weak detector is noisy** → two-tier interpretable gate + held-out calibration; single soft signal cannot trigger a retry.
- **Detector/thresholds overfit the tiny calibration set** *(new)* → disjoint dev/validation/test; never report the tuning set as improvement; bootstrap CIs; untouched broader run for the final claim.
- **GT clause refs are incomplete** → GT is an incomplete silver oracle; pool + expert-adjudicate alternative support; report both silver-GT and pooled-expert metrics.
- **Graph expansion hub-drift / Static-Graph-Fallacy** *(new)* → rarity-gate + Stage-1 concept reuse first; degree-normalized PPR / bridge as escalation; hub penalty; provenance map-back; test widened retry before graph expansion.
- **Refactor breaks `graphont`** → byte/structure parity traces before activating the new mode.
- **Retries add cost without value** → add actions one at a time; oracle-derived routing; 0/1/2 ablation; harmful-retry rate tracked.

## 15. Summary

Phase 12 rev 02 keeps the original scope and all locked decisions, and hardens the three places the research critique flagged:
1. **detector** → two-tier deterministic gate over pre-generation, rank-normalized signals (citation-presence removed from runtime);
2. **graph expansion** → typed, hub-safe, provenance-first;
3. **evaluation** → disjoint splits, action-oracle-derived routing, pooled adjudication, counterfactuals, with **retrieval recall as the primary success metric and D6 as observational**.

Implementation order: define weak retrieval from real held-out cases → expose/analyze signals → split retrieval from packing → two-tier weakness gate → parameter retry → typed hub-safe graph expansion → oracle-derived routing → evaluate whether retrieval recall improved (D6 observed, not gated).
