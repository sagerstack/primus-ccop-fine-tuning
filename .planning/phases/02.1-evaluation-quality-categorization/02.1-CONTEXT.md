# Phase 2.1: Evaluation Quality Categorization - Context

**Gathered:** 2026-03-19
**Status:** Ready for planning

<domain>
## Phase Boundary

Categorize all 6 evaluation metrics into 3 diagnostic groups, aggregate RAGAs metrics at benchmark and overall levels (currently only per test case), display categorized summaries in CLI, reorganize per-test-case panels, and persist categorized aggregates in JSON result files. No changes to scoring logic, rubrics, or evaluation pipeline mechanics.

</domain>

<decisions>
## Implementation Decisions

### Category Grouping & Labeling
- Three groups, no letter prefixes (just named):
  - **Retrieval Quality** — RAGAs: context_recall, RAGAs: context_precision
  - **Model-RAG Grounding** — RAGAs: faithfulness
  - **Model Response Quality** — LLM Judge (0-3), RAGAs: answer_correctness, RAGAs: answer_relevancy
- LLM Judge score sits inside Model Response Quality group (not separate)
- RAGAs metrics prefixed with "RAGAs:" in all display
- LLM Judge labeled as "LLM Judge" (no prefix)

### Aggregation Levels & Formulas
- Four display levels, always shown regardless of run scope:
  1. Per-test-case — individual scores (existing panels, reorganized into 3 groups)
  2. Per-benchmark — simple average across test cases within each benchmark
  3. Overall — weighted average across benchmarks using existing category weights:
     - Regulatory Applicability & Interpretation: 25% (B1-B5)
     - Compliance & Risk Reasoning: 25% (B6-B12)
     - Remediation & Audit Reasoning: 20% (B13-B16)
     - Governance & Consistency (SG Context): 10% (B17-B19)
     - Safety & Regulatory Grounding: 20% (B20-B21)
- LLM Judge score normalized to 0-1 (matches RAGAs scale) for aggregation
- Just mean, no min/max
- RAGAs errors (evaluation_error=True) counted as 0 in averages
- In llm-only mode, Retrieval Quality and Model-RAG Grounding groups show "N/A"
- Rule-based benchmarks (B1, B2, B4, B5, B6, B21): handle as current — their overall_score fills the benchmark score slot. LLM Judge row shows the rule-based score in the categorized view.

### CLI Summary Display
- Categorized quality summary **replaces** existing Evaluation Summary table (model, tests, passed, duration info incorporated into new view)
- Per-benchmark categorized table **replaces** existing Results by Benchmark table
- Single Rich table with group header rows separating the 3 categories
- Per-benchmark table shows all 6 individual metrics per benchmark (not just group averages)
- Per-test-case panels reorganized into 3 groups (matching summary structure):
  - Model Response Quality section: LLM Judge dimensions + RAGAs: answer_correctness + RAGAs: answer_relevancy
  - Model-RAG Grounding section: RAGAs: faithfulness
  - Retrieval Quality section: RAGAs: context_recall + RAGAs: context_precision

### JSON Persistence
- Categorized aggregates stored in metadata section as new `quality_categories` field
- Per-test-case ragas data restructured from flat `ragas.metrics` array into grouped structure (retrieval_quality, grounding, response_quality)
- JSON includes group definitions (which metrics belong to which group) — self-describing
- Breaking change acceptable — old result files without categorized fields are obsolete
- Group definitions + scores at both overall and per-benchmark levels in metadata

### Claude's Discretion
- Exact Rich table formatting and column widths
- How to incorporate model/tests/passed/duration info into the new summary layout
- Exact JSON field naming conventions within the grouped structure
- How to handle single-benchmark runs vs multi-benchmark runs in the summary display (same structure, just fewer rows)

</decisions>

- Consistency across all levels: per-test-case panels, per-benchmark table, and overall summary all use the same 3-group structure
