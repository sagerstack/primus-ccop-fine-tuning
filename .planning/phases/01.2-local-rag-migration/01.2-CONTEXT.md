# Phase 1.2: Local RAG Migration - Context

**Gathered:** 2026-03-01
**Status:** Ready for planning

<domain>
## Phase Boundary

Migrate RAG infrastructure from Databricks (Mosaic AI Vector Search + managed BGE embeddings) to a fully local stack (Qdrant + sentence-transformers BGE-large-en). Introduce port/adapter abstractions for vector store and indexing so the implementation is swappable. Keep Databricks code as an alternate adapter behind the new ports. Existing LangGraph adaptive RAG pipeline (query analysis, retrieval, grading, generation, fallback) stays intact -- only the vector store and embedding layers change.

Phase 1 Plan 05 (Databricks-specific tests) is skipped. This phase includes its own testing for the Qdrant-based pipeline.

MLflow migration (Databricks MLflow to local) is NOT in this phase -- it stays in Phase 1.1 Plan 03 with target changed from Databricks to local file-based storage.

</domain>

<decisions>
## Implementation Decisions

### Vector Store
- Qdrant as the local vector store (replaces Databricks Mosaic AI Vector Search)
- Qdrant runs locally via Docker container
- Native hybrid search (dense + sparse) replicates the current Databricks RRF-based hybrid search
- Metadata filtering preserved (document_source, section, clause, citation_id, document_type)

### Embedding Model
- BAAI/bge-large-en-v1.5 via sentence-transformers (replaces Databricks managed BGE endpoint)
- Runs locally on Mac (MPS backend on Apple Silicon, CPU fallback on Intel)
- Same model as Databricks setup -- embedding space is identical, retrieval behavior preserved
- One-time model download (~1.3GB), cached locally after first use

### Architecture (Port + Adapter Pattern)
- Create IVectorStore / IIndexer ports in the domain layer
- QdrantAdapter implements IVectorStore for retrieval
- QdrantIndexer implements IIndexer for ingestion
- DatabricksAdapter and DatabricksIndexer retained as alternate implementations behind the same ports
- DI container selects adapter based on configuration (.env.local)
- Aligns with existing Clean Architecture pattern (IRagPipeline port already exists)

### Migration Approach
- New phase (1.2), not a rework of Phase 1
- Phase 1 Databricks code stays as alternate adapter (not deleted)
- LangGraph pipeline internals unchanged -- only the retriever initialization and embedding source swap
- Retrieval node switches from `DatabricksVectorSearch` to Qdrant retriever (behind IVectorStore port)
- Ingestion orchestrator (`run_ingestion.py`) calls IIndexer instead of DatabricksIndexer directly
- Configuration via .env.local: new Qdrant-specific settings, Databricks settings become optional

### Databricks Code Disposition
- Keep DatabricksIndexer (554 lines) as alternate adapter behind IIndexer port
- Keep DatabricksVectorSearch retrieval as alternate adapter behind IVectorStore port
- Databricks dependencies remain in pyproject.toml as optional (not required for local-only setup)
- Config: Databricks settings remain optional -- if not set, Qdrant is used by default

### Phase 1 Plan 05
- Skipped entirely -- was designed for Databricks-specific E2E tests
- This phase includes its own unit tests and E2E verification for the Qdrant-based pipeline

### Claude's Discretion
- Qdrant collection configuration (distance metric, vector size, HNSW params)
- Sparse vector implementation approach (BM25 or SPLADE for hybrid search)
- IVectorStore / IIndexer port method signatures (based on what both adapters need)
- Docker Compose configuration for Qdrant
- Test structure and fixtures
- Error handling and retry logic for Qdrant operations

</decisions>

<specifics>
## Specific Ideas

- Portability is the primary motivation -- don't want to be locked into Databricks ecosystem
- BGE-large-en chosen specifically because it's the same model as Databricks, preserving embedding consistency
- Qdrant chosen for native hybrid search support -- directly maps to current Databricks RRF-based hybrid dense+sparse search
- The port/adapter abstraction should make future vector store swaps trivial (config change, not code change)

</specifics>

<deferred>
## Deferred Ideas

- MLflow migration (Databricks to local) -- stays in Phase 1.1 Plan 03, just change target to local file-based storage
- Re-ingestion optimization (incremental updates) -- not needed for current ~1000 chunks scale
- Embedding model comparison (BGE vs OpenAI vs others) -- could be a future experiment but not part of migration

</deferred>
