## What Was Built

### QdrantVectorStoreAdapter (Retrieval)
Implements `IVectorStore` port for Qdrant hybrid search operations:

**Hybrid search mechanism:**
- Dense embedding via `embedding_service.embed_query()` (BGE with query prompt)
- Sparse embedding via `embedding_service.embed_sparse()` (BM25)
- Qdrant `query_points()` with prefetch + RRF fusion:
  - Prefetch 1: Dense vector search (limit: k * 2)
  - Prefetch 2: Sparse vector search (limit: k * 2)
  - Fusion: Reciprocal Rank Fusion (RRF) to combine results
  - Final limit: k

**Metadata filtering:**
- Translates dict format (`{"document_source": "CCoP 2.0"}`) to Qdrant `Filter` objects
- Uses `FieldCondition` with `MatchValue` for field matching
- Applied via `query_filter` parameter in `query_points()`

**Document conversion:**
- Converts `ScoredPoint` to LangChain `Document`
- `page_content`: from payload "text" field
- `metadata`: all payload fields except "text"
- Returns `List[tuple[Document, float]]` (Document, score pairs)

**Logging:**
- Query preview (truncated to 80 chars)
- Result count and score range (min/max) at INFO level
- Filter details at DEBUG level

### QdrantIndexerAdapter (Indexing)
Implements `IIndexer` port for Qdrant collection creation and chunk indexing:

**Collection setup:**
- Deletes existing collection if present (local dev clean slate)
- Creates collection with hybrid vector config:
  - Dense: `VectorParams(size=1024, distance=Distance.COSINE)`
  - Sparse: `SparseVectorParams(modifier=Modifier.IDF)` — **CRITICAL for BM25 semantics**

**Indexing process:**
1. Extract texts from chunks
2. Generate dense embeddings in batch (`embed_documents()`)
3. Generate sparse embeddings in batch (`embed_sparse_batch()`)
4. Build `PointStruct` for each chunk:
   - ID: Deterministic UUID from `uuid.uuid5(NAMESPACE_URL, chunk.id)`
   - Vectors: `{"dense": [...], "sparse": SparseVector(...)}`
   - Payload: All metadata fields + text + chunk_id
5. Upload in batches of 100 with `wait=True`

**Metadata preservation:**
All fields from `ChunkMetadata` preserved in Qdrant payloads:
- `text` (chunk content)
- `chunk_id` (original chunk.id)
- `document_source`, `section`, `subsection`, `clause`
- `citation_id`, `document_type`
- `page` (optional, only if present)

**Verification:**
- Gets collection info (point count)
- Runs sample hybrid search query
- Returns dict with:
  - `collection_name`, `point_count`, `result_count`
  - `results`: Sample with citation_id, section, score

## Technical Decisions

### 1. Prefetch + RRF Fusion for Hybrid Search
**Decision:** Use Qdrant's native prefetch mechanism with RRF fusion

**Rationale:**
- RRF is rank-based: doesn't require score normalization across dense/sparse vectors
- Handles incompatible score distributions (dense: cosine similarity, sparse: BM25)
- Qdrant optimizes parallel execution of prefetch queries
- Research shows 85% NDCG@10 vs 72% for dense-only

**Implementation:**
```python
results = client.query_points(
    collection_name=...,
    prefetch=[
        Prefetch(query=dense_vector, using="dense", limit=k * 2),
        Prefetch(query=sparse_vector, using="sparse", limit=k * 2),
    ],
    query=FusionQuery(fusion=Fusion.RRF),
    limit=k,
    ...
)
```

**Why k * 2 for prefetch limits:**
- Over-fetch to ensure RRF has sufficient candidates
- Common pattern in hybrid search to improve fusion quality

### 2. IDF Modifier in Collection Config
**Decision:** Set `modifier=Modifier.IDF` in sparse vector config

**Context from research:**
- FastEmbed BM25 outputs raw term frequencies
- Qdrant applies IDF weighting server-side IF modifier configured
- Without IDF modifier, sparse vectors lose BM25 semantics

**Critical pitfall avoided:**
Research flagged this as Pitfall 5 - "BM25 Sparse Vectors Without IDF Modifier". Missing this config would silently degrade hybrid search quality.

### 3. Delete+Recreate Collection Strategy
**Decision:** Delete existing collection before creating new one

**Rationale:**
- Local development environment - clean slate is acceptable
- Simpler than update logic (no point ID reconciliation needed)
- Ensures no stale data from previous runs
- Fast for small CCoP corpus (~100-500 chunks)

**Trade-off:**
- Production environment would need incremental update strategy
- Current approach loses data on re-index
- Acceptable for local RAG migration phase

**Alternative for production:**
```python
# Instead of delete+create:
if client.collection_exists(collection_name):
    client.upsert(...)  # Update existing points
else:
    client.create_collection(...)
```

### 4. Deterministic UUID for Point IDs
**Decision:** Use `uuid.uuid5(NAMESPACE_URL, chunk.id)` for point IDs

**Rationale:**
- Qdrant requires UUID or integer for point IDs
- Chunk IDs are strings (e.g., "CCoP-2.0.5.5.2.1-chunk-0")
- uuid5 generates deterministic UUID from string (same input → same UUID)
- Enables re-indexing without duplicate points

**Why NAMESPACE_URL:**
- Standard UUID namespace for name-based generation
- Provides collision resistance across different chunk ID schemes

**Why not integer hash:**
- Hash collisions possible (Python hash is 64-bit)
- UUID provides stronger uniqueness guarantees

## Known Limitations

1. **Local-only delete+recreate strategy:** Production would need incremental update logic with point ID matching. Current approach acceptable for local dev.

2. **No batch size configuration:** Hardcoded 100 points/batch in indexer. Could expose as parameter if needed for larger corpuses.

3. **No progress callback:** Indexing logs progress but doesn't provide callback mechanism for UI integration. Fine for CLI-based ingestion.

4. **Filter translation limitations:** Current implementation only supports simple equality filters (`MatchValue`). Range queries, nested conditions not yet supported. Sufficient for current metadata schema.

5. **No error recovery:** Batch upload failures abort indexing. Could add retry logic or partial success handling for production robustness.
